## Source file `src/constructs/arguments_parser.rs`

(Relevant parts extracted manually from Opus' prompt output.)

1. Duplicated comment-node reconstruction (maintainability).
Lines 124–127 are byte-for-byte identical (same code and same explanatory comment) to nodes_parser.rs:593–596:
let content_span = Span::new(post_space.start - content.len(), post_space.start);
let start_span = Span::new(token.span.start, content_span.start);
let kind = NodeKind::comment(start_span, content_span, *post_space);
Two independent sites reconstruct the three sub-spans of a Comment token. A shared constructor — e.g. NodeKind::comment_from_token(&token) or a helper on TokenKind::Comment — would DRY this and keep the "span = delimiter + content + post-space" invariant in one place. Low priority, but this is exactly the kind of parallel logic that drifts.

2. Eager display allocation in the expression command path (efficiency).
parse_expression_node, line 220:
let display = format!("{}{}", escape_char, name);
This String is built for every command-in-expression dispatch (\frac1\alpha, etc.) but is consumed only on the rare requires-arguments error branch inside dispatch_expression_invocation (lines 271–274). The Specials arm already passes a borrowed name with no allocation (line 251). Consider deferring the format into the error branch (or passing the pieces) so the common zero-arg dispatch doesn't allocate. Micro-optimization — flagging because it's a per-invocation cost on the hot path, and the fix is local.

3. GroupArgumentParser fallback consumes a group of any class (design note, not a bug).
When the delimited-form class check fails (line 415), control falls to parse_expression_node, whose GroupOpen arm accepts a group of any class in scope (lines 205–213). So \frac[x]{y} — with […] registered as a group class — would swallow the whole [x] bracket group as \frac's first argument rather than treating [ as a single char. This matches the documented "expression = a delimited group of any class in scope" semantics and isn't exercised by the test rules (only brace is registered), so it may be fully intended. Worth a one-line doc note on GroupArgumentParser if the intent is specifically "my class as a group, everything else as a single token," since a reader could reasonably expect the fallback to be char-only.

Regarding Test coverage. One small gap I'd suggest: there's no test for a mandatory group argument whose delta affects tokenization interacting with the noise scan — e.g. a comment appearing in the noise while comments are disabled by the argument's delta. per_argument_state_delta_scopes_the_arguments_extent covers the delta scoping inside the group, but not a noise-scan token classified under the argument delta. Likely fine given scan_argument_noise runs under cx.state (the argument state), but it's an untested corner.

## Source file `src/constructs/nodes_parser.rs`

(Phase 6.2 — content dispatch loop core. Reviewed by an Opus agent; no correctness bugs found. Findings lean toward maintainability, robustness, and test gaps.)

**1. Comment sub-span reconstruction is duplicated and fragile (maintainability / robustness) — `nodes_parser.rs:593-596`, duplicated at `argument_parsers.rs:120-127`**
The three comment sub-spans are reconstructed by byte arithmetic:
```rust
let content_span = Span::new(post_space.start - content.len(), post_space.start);
let start_span = Span::new(token.span.start, content_span.start);
```
This exact block (comment included) is copy-pasted in `argument_parsers.rs:124-127` — the existing report already flagged this, and it's confirmed identical. Two concerns:
- The reconstruction only works because `TokenKind::Comment.content` is currently a raw source slice (`&'s str`), so `content.len()` equals its byte span (`token/token.rs:92-94`). It carries the content *string* but not a content *span*. Any future normalization/decoding of comment content (or a reader that synthesizes content) silently breaks both the span math and the partition invariant.
- `post_space.start - content.len()` is unchecked `usize` subtraction (line 594). It cannot underflow with today's invariants (content sits after a ≥1-byte start delimiter), but CLAUDE.md forbids panic paths in lib code, and this one is one broken invariant away from a debug panic / release wraparound.

Suggested fix: have `TokenKind::Comment` carry the content span (or start-delimiter span) directly, or add one shared helper (e.g. `fn comment_subspans(token) -> (Span, Span, Span)`) used by both call sites. Either removes the duplication and the fragile subtraction at once.

**2. `GroupClose` stop matching is correct — the `]`-closes-`{` class-vs-delim bug is handled (design-note / not a bug) — `nodes_parser.rs:393-398`, `716-728`**
The docs warn about a close matching on class alone. The code correctly requires *both* `delim == close` **and** `group_close_type(state, delim) == Some(*group_type)`, re-resolving the class against the same `cx.state` the tokenizer used. The four adversarial cases (shared class + different delim, reclassifying delta, expected-close path, delimiter-table path) are each covered by a dedicated test (`nodes_parser.rs:1337-1408`). Calling this out explicitly so it is not re-flagged: working as designed.

**3. `.expect("the node was just staged")` is a library-code panic path (robustness, low) — `nodes_parser.rs:375`**
`test_node_stop` does `staged.get(id).expect(...)`. It is a genuine internal invariant (the id was just returned by `stage`), so it cannot realistically fire, but it is the one non-debug `expect` on the hot path and technically violates the "never panic in lib code" rule. Acceptable as-is; if you want strictness, treating a missing id as "condition did not fire" (`false`) would degrade gracefully instead of aborting. Low priority.

**4.** *(fixed July 2026 — the `resume_pos` advancement contract is now documented on `TokenRecovery` and enforced by the recovery arm, which aborts instead of spinning; pinned by a violating-reader test.)*

**5. Deferred diagnostic when a node condition pre-empts an unresolvable command (design-note / test-coverage) — `nodes_parser.rs:423-428`**
In `recover_as_chars`, if `flush_through` reports the node condition fired on the preceding run, the function returns `Ok(true)` *before* `cx.recover(...)`, so the "cannot resolve command" diagnostic is not emitted and the command token is left unconsumed for re-processing. This is consistent (the diagnostic is emitted when the caller re-encounters the command), but it means diagnostic count depends on whether a node condition is active — a subtle behavior with no test. Worth a one-line test asserting the diagnostic is deferred (not lost), or a doc note on the intended ordering.

**6. Minor test-coverage gaps for consume/predicate/callable-node paths (test-coverage) — tests region `nodes_parser.rs:1259-1602`, `1717-2119`**
Coverage is broad, but a few decided behaviors lack a direct test:
- `consume = true` is exercised only for `Command` (line 1453) and `GroupClose` (1479); not for `ParagraphBreak` or `Predicate` stop kinds (the post-space handling differs — a `ParagraphBreak`/predicate-matched comment carries post-space that `move_past(..., true)` would swallow).
- The node stop condition firing on a `Callable` (invocation) node — groups are covered (`node_condition_counts_a_group_as_one_node`, 2208) but dispatched invocations are not, despite `dispatch_invocation` ending in `test_node_stop` (line 474).
None are correctness concerns; they're the untested corners of otherwise-tested machinery.

**7. State is correctly restored on the error path (invariant, confirmed OK) — `nodes_parser.rs:462-466`, `698-701`**
Both descent sites do `cx.state = outer_state;` *before* the `?` on the child parser's result, so an aborting sub-parse never leaks the swapped child state to the caller. The invocation after-effect delta is applied to the loop's own state (line 472) and later discarded by the caller's own structural revert. Verified correct; flagged so it isn't mistaken for a leak.

**Summary:** No correctness bugs found. Prioritize **#1** (unify + harden the comment sub-span reconstruction — duplicated across two files and the only fragile arithmetic in the module). **#5** is cheap robustness/clarity hardening. The rest are low-priority notes.

## Source file `src/constructs/group_parser.rs`

(Phase 6.3 — groups. Reviewed by an Opus agent; no correctness bugs found. `cargo test group_parser` passes 2/2.)

**Summary:** A clean, correct implementation. Both priority-1 concerns check out: the GroupClose stop condition passes **both** `group_type` and `close` (`group_parser.rs:104-107`) and `NodesParser::token_stop` matches them conjunctively (`delim == close && group_close_type(...) == Some(*group_type)`, `nodes_parser.rs:393-397`), excluding the `]`-closes-`{` and reclassified-`}` bugs. Structural state is reverted before any `?`, so no state leaks on abort. Span arithmetic partitions correctly in all three exit paths.

**1. State revert is correctly abort-safe — verified, not a bug (correctness) — `group_parser.rs:111-114`.** `cx.state` is restored (`cx.state = outer_state`) *before* `result?` unwinds, so a strict-mode abort inside the interior parse leaves `cx.state` at the caller's value. Same pattern in the two `cx.recover(...)?` recovery branches. Flagged as a positive because it's the easiest thing to get wrong here.

**2. `unreachable!` on `StopCause::NodeCondition` panics in release (robustness / design-note) — `group_parser.rs:144-146`.** The branch is genuinely unreachable — `GroupParser` builds its `StopSpec` via `StopSpec::at_token(...)`, which sets `node: None` (`nodes_parser.rs:175-177`), so `NodesParser` can never return `NodeCondition`. This mirrors an existing `unreachable!` in `nodes_parser.rs:282`, so it's consistent with codebase convention and defensible as an invariant assertion; still worth a conscious call on whether these should be `debug_assert!`-guarded or folded into the `EndOfInput` handling. Low priority.

**3. EOF end position relies on reader `pos()` semantics — verified correct (correctness) — `group_parser.rs:131`.** Uses `cx.tokens.pos()` as the group's `end` in the unclosed-at-EOF path. After the interior parse hits `EndOfStream`, `NodesParser` flushes the terminal token's pre-space (trailing whitespace) into the interior siblings and does `move_to(&token, false)`, leaving `pos() == EndOfStream.span.start`, which equals the end of the last flushed interior node. So the partition invariant holds for `"{"`, `"{ab"`, and `"{ab  "` alike, and `StdTokenReader`/`TokenListReader` agree. Correct — noted because it's non-obvious and depends on the NodesParser flush contract.

**4. `UnexpectedGroupClose` diagnostic wording (maintainability) — `group_parser.rs:138`.** Emits `"unclosed group: expected '{close}'"` for what is actually a *mismatched / stray* close (a `]` under a `{`, or a re-classed `}`), pointing at the stray token's span. Consider distinct wording (e.g. `"mismatched group close: expected '{close}'"`) to help users distinguish the two recovery situations from the EOF message. Cosmetic.

**5. Own-file test coverage is thin; substantive paths covered by integration tests elsewhere (test-coverage) — `group_parser.rs:253-282`.** Only two direct-drive tests (well-formed round-trip under `Strict`; unclosed-at-EOF under `Tolerant`). Not exercised via the direct-drive harness: the `UnexpectedGroupClose` unwind, strict-mode abort (EOF and mismatch), `with_child_states`, nested groups, ambiguous-`$` interior-state derivation. These *are* all covered by `nodes_parser.rs` integration tests (e.g. `unclosed_group_strict_aborts`, `mismatched_close_inside_a_group_unwinds_without_consuming`, `ambiguous_dollar_group_closes_via_the_derived_expected_close`, `sibling_group_interiors_share_one_memoized_state`). Coverage is adequate overall; optional to make the file self-covering.

**6. `self.child_states.clone()` on each parse (efficiency) — `group_parser.rs:110`.** The clone is shallow (Arcs + borrowed `&dyn Fn`), so cost is negligible. `core::mem::take(&mut self.child_states)` would avoid it entirely, but `&mut self` permits re-invocation in principle, so the defensive clone is reasonable. Trivial; leave as-is.

**7. Doc-reference precision (maintainability / doc-note) — `group_parser.rs:25`.** The module header cites "(DESIGN_RATIONALE.md §3.6, §3.8)" for matching-and-recovery, but the rule that an unclosed group records an **empty `close` TextContent** is documented in §3.5 (alongside the `GroupData` definition). Adding §3.5 to the header cross-reference would be accurate. Cosmetic.

**Checked and found correct:** GroupData construction (`group_type: Some`, span-backed `open`/`close`, `ext: Default`); the recorded close is the exact delimiter span (GroupClose tokens carry no post-space); interior-state derivation goes through the session memo (`group_interior_state`) which always sets `expecting_group_close = rule`, guaranteeing the close stays recognizable (the `$…$` case); the outer (restored) state is attached to the group node while children were staged under the interior state; naming conforms to NAMING_STRATEGY.

## Source file `src/constructs/invocation_parser.rs`

(Phase 6.4/6.5 — invocation dispatch. Reviewed by an Opus agent; no correctness bugs found. All 24 argument tests pass.)

**Overall:** A clean, well-documented file that correctly implements the Phase 6.4/6.5 contract. The critical invariants — whole-trigger consumption, non-over-claimed post-space, per-argument state scoping with pre-`?` revert, and coordinate consistency between the flat child list and region-relative content offsets — all hold. Findings are minor plus one genuine test-coverage gap.

**1. Post-space handling is correct — no over-claiming, no double-count (correctness, verified) — `invocation_parser.rs:164`.** `post_space: TextContent::Spanned(token.post_space())` records exactly the trigger token's own syntactic post-space (`Command`/`Comment` kinds only; empty span at `span.end` otherwise, `token.rs:149-156`), matching the July 2026 amendment. The dispatch arm consumes the trigger whole first (`nodes_parser.rs:459`, `move_past(invocation.token, true)`), so `cx.tokens.pos() == token.span.end` on entry and `scan_argument_noise` cannot re-scan the post-space bytes. For `\frac 1 2` the recorded post-space sits between name and first region (span `5..6`); for `\& b` it is empty and the following space falls through to the caller as sibling content. Flagged as highest-priority because it is the file's riskiest invariant and it holds.

**2. Span-end relies on "last staged child is the source-rightmost node" (maintainability) — `invocation_parser.rs:149-155`.** `end` is taken from `children.last()`'s span end — correct for every standard argument shape, but an unstated invariant rather than a computed maximum. Since `parse_declared_arguments` is shared with the Phase 6.6 environment-shaped compositions (`invocation_parser.rs:85`), a future custom `ArgumentParser` whose region ends on a non-rightmost node would silently produce a too-short node span. Suggest a one-line comment pinning the assumption at line 149 (computing a `max()` is a per-invocation cost you likely don't want).

**3. Zero-arg / single-char-command post-space cases untested directly (test-coverage) — recommended action.** The 24 tests exercise `StdInvocationParser` end-to-end well, but two gaps: (a) no direct test of a callable with **zero declared arguments** asserting the trigger-only span and `post_space` (`\alpha` is dispatched in `expression_fallback_dispatches_a_full_invocation` but its span/post_space are never asserted); (b) the module's headline amendment example — a **single-character command** like `\& b` where post-space is empty and the trailing space must become sibling content — is not tested anywhere. Suggest adding: a zero-arg macro `\x` in `\x y` asserting `span == 0..2`, `post_space == ""`, sibling `" y"`; plus a multi-char `\x y` variant asserting `post_space == " "` and span including it. This is the exact behavior the July 2026 amendment turns on, only tested indirectly.

**4. Per-argument state restore is not unwind-safe (robustness, low) — `invocation_parser.rs:96-98`.** `cx.state` is swapped to `argument_state` and restored by plain assignment after `parse_argument`. If the argument parser panics, `cx.state` is left as the argument state. Acceptable under the project's abort-not-panic policy (an unwind tears down the borrowed `cx`), and `result?` propagates *after* the restore so the ordinary `Err` path leaks nothing. A `scopeguard`/`Drop`-based restore would be over-engineering. No change recommended.

**5. Per-invocation `Vec` allocations lack capacity hints (efficiency, low) — `invocation_parser.rs:89-90`.** `arguments` grows to exactly `argument_specs.len()`; `Vec::with_capacity(argument_specs.len())` avoids reallocation on multi-argument callables. Combined with the per-invocation `Box<dyn ConstructParser>` (decision 2's noted cost) and the required owned name copy (`name.into()`, line 160 — necessary), the hot path does several small allocations; only the `arguments` capacity hint is a free win. Minor.

**6. `.expect` builder read-backs (robustness, design-consistent) — `invocation_parser.rs:152`.** `.expect("the child was just staged")` is a panic in lib code, but it is the established builder-readback idiom (same pattern in `argument_parsers.rs:461`, `builder.rs`) governed by the builder's documented "panic on caller bug" policy. Unreachable in practice. Consistent with design; no change.

**7. Coordinate handling between flat child list and region-relative content is correct (correctness, verified) — `invocation_parser.rs:100-108`.** `children.extend_from_slice(&region.nodes)` builds one flat list across all arguments; `ChildRegion::new(start..end, region.content)` stores region offsets in combined-list coordinates while `region.content`'s `InRegion(..)` stays region-relative. Traced against `builder.rs:306-311`, which resolves `InRegion(r)` off the *resolved* region start — so the two coordinate bases compose correctly (e.g. `\frac 1 2` arg1 resolves content to `"2"`, not the noise space). No off-by-one. Confirmed by `single_token_fallback_stages_whitespace_as_region_noise`.

**Net:** No blocking issues. Recommended action is **#3** (add the zero-arg / single-char-command post-space tests), plus optionally the **#2** comment and **#5** capacity hint.

## Source file `src/token/list_reader.rs`

(Phase 6.1 — `TokenListReader`, a `TokenReader` over a pre-built `Vec<Token>` for isolated construct-parser tests. Reviewed by an Opus agent; a faithful reimplementation, 8/8 tests pass. `move_past`/`move_to`/`pos` are byte-for-byte identical to `StdTokenReader` and compute purely from the passed token's spans, so all fidelity risk concentrates in `peek` + `current()`.)

**1. Synthesized EndOfStream is a second, undocumented divergence from `StdTokenReader` (fidelity / design-note) — `list_reader.rs:89-93`.** The module doc (lines 18-23) claims the *only* inherent difference is the fixed list's inability to re-scan under momentary state. But the `None` branch synthesizes `EndOfStream` as `Span::empty(self.pos)` with **empty pre_space**, which diverges independently of re-scanning. Scenario: build a list from `scan("x  ")` but omit the trailing EOS token → `[Char('x') 0..1]`. After `next()`, `pos = 1`, and `peek()` yields `EndOfStream { span: empty(1), pre_space: empty(1) }`, whereas `StdTokenReader` on the same content yields `EndOfStream { span: empty(3), pre_space: 1..3 }` — both the terminal byte position and the trailing-whitespace pre_space differ. The root cause is inherent (a list without a trailing EOS carries no content-length or trailing-whitespace info), so it is not fixable in code, but the doc overstates equivalence: lines 18-23 and line 41 should be amended to note a synthesized EOS cannot reproduce trailing-whitespace pre_space or a terminal position beyond the last token's `span.end`. In practice `scan()` always appends EOS, so tests don't hit it.

**2. The documented `\verb`/in-span divergence is asserted nowhere (test-coverage) — tests around `list_reader.rs:230-235`.** The headline fidelity limit — `move_past(tok, false)` landing *inside* a token's span, after which `peek` returns the *following* listed token rather than re-scanning the post-space bytes (lines 18-23) — is never pinned by a test. `move_past_and_move_to_flags_match_std_reader` sets `pos = 6` via `move_past(false)` and checks `pos`, but never `peek`s there. A future change to `current()` could silently alter this behavior with all tests green. Suggest a test that, at that in-span position, asserts `TokenListReader` yields the following token AND explicitly asserts it differs from `StdTokenReader` — turning the prose contract into an executable one.

**3. `current()` lookup is correct and efficient — confirms faithful positioning (correctness, positive) — `list_reader.rs:69-72`.** `partition_point(|t| t.span.start < self.pos)` returns the first token with `span.start >= pos`. Because `pre_space.end == span.start` by convention, for any position at or before a token's start the clip `pre_space.start.max(pos).min(pre_space.end)` reproduces `StdTokenReader`'s `skip_whitespace`-derived pre_space exactly (verified against `reader.rs:157-158`). O(log n), not a linear scan. The `.min(pre_space.end)` also defensively prevents an inverted span if a hand-built token violates adjacency. This is the core of the file and it is sound.

**4. `move_past(tok, false)` can panic on subtraction underflow for hand-built tokens (robustness) — `list_reader.rs:101`.** `self.pos = tok.span.end - tok.post_space().len()` underflows (panic) if a hand-constructed token has `post_space().len() > span.end`. `StdTokenReader` has the identical line (`reader.rs:390`), so it's parity, not a regression — but this reader's entire purpose is hand-built lists, where malformed tokens are far more likely. Consider a `debug_assert!(tok.post_space().end <= tok.span.end)` to fail loudly rather than underflow-panic.

**5. `move_to_pos` drops the boundary/bounds guards `StdTokenReader` has (robustness / maintainability) — `list_reader.rs:64-66`.** `StdTokenReader::move_to_pos` (`reader.rs:141-145`) debug-asserts `pos <= content.len()` and char-boundary; this version sets `self.pos = pos` with no checks. There's no content here so those exact checks don't apply, but an out-of-order position silently produces the "following token" behavior with no diagnostic. Low priority given the fidelity limit is documented; a debug-only sanity note would help hand-built-list authors.

**6. `new()`'s invariant check is weaker than what `peek` relies on (maintainability) — `list_reader.rs:50-53`.** The debug_assert verifies only ascending, non-overlapping spans (`w[0].span.end <= w[1].span.start`). But `peek`'s clip fidelity additionally relies on `pre_space.end == span.start` and each token's pre_space lying in the gap after the previous token (`w[1].pre_space.start >= w[0].span.end`). A list satisfying the span-order assert but violating pre_space adjacency would clip incorrectly with no early warning. Consider strengthening the assert to also check these.

**7. `move_past`/`move_to` accept any token without verifying list membership (design-note) — `list_reader.rs:97-111`.** Both compute the new position purely from the passed token's span fields and never confirm the token came from `self.tokens`; a foreign/stale token silently repositions to arbitrary bytes. This mirrors `StdTokenReader` (intentional — the trait contract is position-from-token), so not a bug; for an isolated hand-built-list harness a membership `debug_assert` would be a cheap safety net.

**Coverage present and good:** round-trip parity against a scanned sequence, lockstep movement-matrix parity vs `StdTokenReader`, idempotent/terminal EOS parity for trailing whitespace *with* the EOS token present, mid-whitespace pre_space clipping, empty list, rewind-to-earlier-token. Main gaps are items 1 and 2.

## Source file `src/node/invariants.rs`

(Phase 6.3 — `check_tree_invariants`, a public test utility validating parsed trees, applied retroactively to the whole suite. Reviewed by an Opus agent. For well-formed parser output, all four rule families are genuinely enforced with no constructible false-pass; the `NodeKind` match is compiler-exhaustive. Findings are mostly latent gaps, robustness, and one notable test-coverage hole.)

**1. No negative tests for the callable/region/post-space logic — the most complex and most-amended code has zero broken-tree tests (test-coverage) — `invariants.rs:402-541`.** The three `#[should_panic]` tests cover only Chars-content, List-sibling-gap, and Group-open-delimiter. There is **no** negative test feeding a deliberately-broken *Callable*: region tiling gap/overlap (`check_regions`, 324-399), children-block non-contiguity (248-271), the revised rule-3 post-space position (226-244), content escaping its region subtree (355-391), nor the reachability/multi-parent/unreachable-node asserts (70-85). Since a false pass is the most damaging bug class here, this means a future refactor could silently weaken exactly the hardest-to-reason-about code. There's also no *positive* callable test in this file (all builders use Chars/Group/List); the callable path is validated only indirectly via `environment_parser.rs`/`argument_parsers.rs`/`nodes_parser.rs`/`node/mod.rs` tests. Suggest `#[should_panic]` tests staging a callable with (a) a region-tiling gap, (b) a post-space whose `end` misses the first child, (c) a node in two children ranges, (d) an unreachable node.

**2. Callable post-space is not verified whitespace-only, and its `start` is loosely bounded (completeness / minor) — `invariants.rs:236-244`.** Rule 3 (DESIGN_RATIONALE §3.5) pins post-space as the trigger token's own syntactic post-space, whitespace-only by construction. The checker asserts `s.end == expected_end && s.start >= span.start` but never checks the payload is whitespace, nor that `s.start` is at/after the name. A malformed post-space swallowing non-whitespace name bytes (`s.start == span.start`, covering the whole `\foo`) would pass. Likely intentional (whitespace is `Lang`-defined and not cheaply checkable here), but worth an explicit note. Same unchecked-whitespace observation applies to Comment `post_space` (160-168).

**3. Comment interior byte-accounting is only checked when *all three* parts are `Spanned` (completeness) — `invariants.rs:169-181`.** The partition `start.end == content.start && content.end == post_space.start` runs only inside the all-`Spanned` `if let`. If `content` were `Owned` while `start`/`post_space` are `Spanned`, an internal gap/overlap between delimiter and post-space would go undetected. Not reachable from current parser output (rule 1 makes fresh comments all-`Spanned`; `materialize()` makes them all-`Owned`), so a latent gap for future synthesized/transformed comments, not a live false-pass.

**4. Group interior arithmetic trusts `Owned` delimiter lengths without verifying they physically occupy the span (design-note / latent false-failure) — `invariants.rs:193-221`.** `text_len` computes the interior as `span.start + open_len .. span.end - close_len` but skips the positional prefix/suffix checks for `Owned` delimiters. For a *synthesized* group whose span covers only its interior with `Owned` delimiters corresponding to no physical bytes (constructible via `GroupData::untyped`), the interior would be miscomputed and the partition check would wrongly fail (or wrongly succeed if lengths line up). Out of current scope (`materialize()` preserves lengths byte-for-byte, per the `accepts_a_materialized_tree` test); worth a one-line comment recording the "span physically contains the delimiters" assumption.

**5. The root skipped-byte exemption described in the module doc is not actually coded (design-note) — `invariants.rs:1-5` + `check_interior_partition:279-306`.** A `List`'s interior is its whole span (186) and the partition is required exact (`pos == interior.end`, 298). When the promised tolerant root recovery that skips a stray close lands, the root `List`'s children won't tile its full span and this checker will panic — there is no exemption path. **1. `first_chars` is dead code, and its doc describes machinery that was deleted (maintainability / documentation) — `prefix_table.rs:52`, `92-98`, `108-112`.**

**2. `match_at` is an unguarded linear scan run on every content character (efficiency) — `prefix_table.rs:104-106`, called from `reader.rs:174`/`276`.**

```rust

```
So every plain letter of the document pays one `str::starts_with` per table entry — for a latexlike preset (`{}`, `[]`, `$`, `$$`, `\(`, `\)`, `\[`, `\]`, …) that is ~8–14 string comparisons per character, for a guaranteed miss. A single first-character membership test (`first_chars`, #1) rejects the overwhelming majority in one short scan; the entry loop then runs only on the ≤1% of positions that can actually start a delimiter. This is the cheapest available win on the tokenizer's hot loop and it needs no new data structure — the data is already built and already cached per state. This is worth more than it looks: `TokenListReader::peek` *relies* on `pre_space.end == span.start` to clip pre-space correctly (`list_reader.rs:69-81`), and the `list_reader` review asked for exactly this check to be added there (its finding 6) — putting it in `Token::new` covers hand-built lists, third-party readers, and finding 3's identity in one place instead of three.

## Source file `src/source/span.rs`

(Phase 1/2 — `Span`, the plain `Copy` byte range on which all span arithmetic in the crate rests: tokens, `TextContent::Spanned`, `TokenError`, every node span before it becomes a `SourceSpan`. 98 lines, 3 tests, all green; full suite 280/280 + 1 doc-test. Reviewed by an Opus agent. **No correctness bug in the file itself** — the type is small and does what it says. The findings are about what the type *doesn't* do: it is the natural home for arithmetic that is currently hand-rolled (and, in two known places, underflow-unsafe) in six other files, and its safety contract is advisory in a way the rest of the `source` module's is not.)

**Summary:** `Span` is correct, minimal, and honest. Its `new()` debug-asserts `start <= end`; `empty()`, `len()`, `is_empty()`, `range()`, `slice()`, `From<Range>` and the compact `Debug` (`3..7`) are all right. But: (a) the fields are `pub`, so the validating constructor is bypassable and *is* bypassed in four places, making the `start <= end` invariant advisory rather than enforced — an asymmetry with `SourceSpan`, whose fields are private; (b) `len()` is an unchecked subtraction, so an inverted span wraps silently in release instead of failing; (c) the three `tok.span.end - tok.post_space().len()` underflow sites flagged by earlier reviews are **not** a missing-`Span`-helper problem — they are algebraically identical to `tok.post_space().start` and can be deleted outright; (d) `Span` and `SourceSpan` do not interoperate — every bridge goes through an untyped `Range<usize>` (21 occurrences of `SourceSpan::new(&cx.source, span.range())`); (e) no `contains` / `overlaps` / `merge` / `get` exist at all, and consumers hand-roll each of them. Test coverage is thin in exactly the areas where the type's contract lives: no multi-byte / char-boundary test, no inverted-span test, no `slice`-panic test.

---

**1. The three `span.end - post_space().len()` underflow sites are removable, not fixable with a new helper (robustness / simplification) — `reader.rs:390`, `list_reader.rs:101`, `environment_parser.rs:651`.**
All three compute "the position just before the token's post-space" as an unchecked `usize` subtraction:
```rust
self.pos = tok.span.end - tok.post_space().len();   // reader.rs:390, list_reader.rs:101
resume_at(cx.tokens, trigger.span.end - trigger.post_space().len());  // environment_parser.rs:651
```
By the token's own documented invariant — post-space is a *trailing sub-range of `span`* (`token.rs:120-123`), enforced at construction (`reader.rs:338`, `reader.rs:375`: the span's `end` **is** `post_space.end`), and for post-space-less kinds `post_space()` returns `Span::empty(self.span.end)` (`token.rs:154`) — the identity

  `span.end - post_space().len()  ==  post_space().end - (post_space().end - post_space().start)  ==  post_space().start`

holds for **every** kind. So all three lines are exactly `tok.post_space().start`. That form cannot underflow, needs no new `Span` API, and degrades gracefully (to a garbage-but-in-range position) rather than panicking on a hand-built `TokenListReader` token whose post-space is malformed — which is precisely the residual risk flagged in the `list_reader.rs` review (item 4) and the `nodes_parser.rs` review (item 1). This is the highest-value action arising from this file's review even though the fix is not *in* this file. (The *other* subtraction, `post_space.start - content.len()` at `nodes_parser.rs:594` / `argument_parsers.rs:125`, is genuinely irreducible: `TokenKind::Comment` carries the content *string* but no content *span*. That one still needs the already-recommended token-level fix — carry the content span — and no `Span` helper rescues it.)

**2. `pub` fields make the `new()` invariant advisory, and it is bypassed today (design / correctness-adjacent) — `span.rs:14-17, 22-25`.**
`Span::new` debug-asserts `start <= end` (line 23), but `start`/`end` are public, so the assert guards one of several construction paths. Four lib-code sites mutate the fields in place, skipping it entirely:
- `nodes_parser.rs:280` `run.end = pre_space.end;`
- `nodes_parser.rs:297` `run.end = token.span.end;`
- `nodes_parser.rs:1956` `content.end = token.span.end;`
- `argument_parsers.rs:659` `span.end = token.span.end;`

All four extend `end` forward (monotone), so none can currently invert a span — but the debug-asserted contract is not what actually holds the line; the parsers' own `debug_assert!(run.end == pre_space.start, …)` contiguity checks (`nodes_parser.rs:274-279, 291-296`) are. This is also an inconsistency inside `source`: `SourceSpan` has **private** fields plus `start()`/`end()`/`range()` accessors and a validating `new()` (`source.rs:188-217`), while its `Copy` sibling is a bag of two public `usize`s. Two coherent positions — (i) accept that `Span` is a transparent value type and demote `new()`'s assert to documentation, or (ii) privatize the fields, add `start()`/`end()`, and let mutation go through an explicit `extend_to(end)` / `with_end(end)` — but the current middle ground gives the *appearance* of an enforced invariant without the substance. Worth a conscious call (user decision; do not change unilaterally).

**3. `len()` wraps silently on an inverted span in release; `is_empty()` disagrees with it (robustness) — `span.rs:33-40`.**
```rust
pub fn len(&self) -> usize { self.end - self.start }
pub fn is_empty(&self) -> bool { self.start == self.end }
```
For `start > end` (reachable via pub fields, or via the `nodes_parser.rs:594` underflow in release), `len()` wraps to a near-`usize::MAX` value while `is_empty()` returns `false` — and the corruption then surfaces far away as an opaque `&content[range]` slice panic ("slice index starts at N but ends at M") inside `slice()`/`TextContent::resolve`, or as a `SourceSpan::new` debug-assert in a completely different module. `self.end.saturating_sub(self.start)` (and `self.start >= self.end` for `is_empty`) costs nothing measurable and turns a wrap into a benign zero. This is a one-line hardening consistent with CLAUDE.md's no-panic rule; whether it is *desirable* to paper over a broken invariant instead of failing loudly is a judgment call — the alternative is a `debug_assert!(self.start <= self.end)` in `len()` itself, which at least names the violation at the point where it matters.

**4. `Span` and `SourceSpan` do not interoperate — the bridge is an untyped `Range<usize>` (API completeness) — `span.rs:42-45`, `source.rs:201, 240`.**
`SourceSpan::new` takes a `Range<usize>`; `Span` offers `range()`; so the crate is littered with `SourceSpan::new(&cx.source, span.range())` — **21 occurrences** (of 31 `SourceSpan::new(&cx.source, …)` calls total; the other 10 build a range by hand from two spans, see finding 5). In the other direction there is nothing at all: `SourceSpan` exposes `start()`/`end()`/`range()` but no `span() -> Span`, so `node/invariants.rs` — the checker for the very invariants this type underpins — works entirely in `Range<usize>` and re-derives everything (`invariants.rs:99`, `106`, `204`, `213`, `221`, `252`). The `Range<usize>` round-trip is lossless, so this is not a bug; it is a missing seam. Two cheap additions would remove most of it: `SourceSpan::span() -> Span` and either `Span::in_source(&Arc<Source<O>>) -> SourceSpan<O>` or `SourceSpan::new_spanned(&source, span)`. Naming: `in_source` reads correctly and carries no competing sibling vocabulary (NAMING_STRATEGY principles 3-4); flagging it as a design question rather than a recommendation because it puts a `SourceSpan`-returning method on the deliberately-`Arc`-free type (the module's cycle-prevention invariant is unaffected — both live in `source` — but the "`Span` is the cheap one" mental model is worth preserving).

**5. Missing operations that consumers hand-roll: `cover`/`merge`, `contains`, `get` (API completeness) — `span.rs:20-56`.**
`Span` has *no* relational or combining operators. Each is hand-rolled where needed:
- **cover / merge** (a span spanning two others): `Span::new(first.start, last.end)` at `nodes_parser.rs:999-1002`; `SourceSpan::new(&cx.source, open_span.start..close_span.end)` at `nodes_parser.rs:1971`; `…, trigger.span.start..body.end)` at `environment_parser.rs:605`; `…, end_token.span.start..name_group.end)` at `environment_parser.rs:260`; the "span-end from the last staged child" idiom at `invocation_parser.rs:149-155`. A `Span::cover(self, other) -> Span` (or `to(self, other)`) would DRY five sites and give the "node span = open .. close" idiom one name.
- **contains** (span-in-span): `span.start <= child_span.start && child_span.end <= span.end` at `invariants.rs:252`; the group-interior arithmetic at `invariants.rs:194-221`.
- **non-panicking slice**: `invariants.rs:106` hand-rolls `source_content.get(s.range()).is_some()` — a `Span::get(content) -> Option<&str>` is the natural companion to the panicking `slice()` and is the one addition that directly serves CLAUDE.md's no-panic rule (`slice()` is reachable from public node accessors via `TextContent::resolve`, and a transform that re-sources a node without materializing its content will hit it).
- **adjacency** (`a.end == b.start`): `nodes_parser.rs:275, 292`; `list_reader.rs:51`. Marginal; a named `abuts` is probably over-engineering.

**Important design note if these are added:** the empty-span semantics of `contains`/`overlaps` must be *decided*, not defaulted. Spans are half-open, and the crate is full of legitimately empty spans (`Span::empty(pos)` for absent pre/post-space, `EndOfStream`, unclosed-group close delimiters). Does `Span::new(2,5)` contain `Span::empty(5)`? Does `Span::empty(3)` overlap `Span::new(3,7)`? Both answers are defensible and both will be depended on silently once shipped. Pin them in the doc comment and in tests at the moment of writing, and record the call in DESIGN_RATIONALE §3.1.

**6. `Copy`/`Eq`/`Hash`/`Debug`/`From<Range>` are all right; `Ord` is absent and should stay absent (trait impls — confirmation) — `span.rs:12, 58-68`.**
- `Clone, Copy, PartialEq, Eq, Hash` derived (line 12) — correct and consistent with the "`Copy`, no `Arc`" mandate (ARCHITECTURE.md §source, NAMING_STRATEGY "Byte range | `Span` (in `source`)").

The inverse `impl From<Span> for Range<usize>` does **not** exist; `range()` covers the need and the type is `Copy`, so this is a cosmetic gap at most (it would allow `SourceSpan::new(&src, span.into())`, marginally worse than the `in_source` helper of finding 4). ## Source file `src/error.rs`

(Phase 1 — `Severity`/`Diagnostic`/`Diagnostics`, the `Recovery` policy, `ParseError`/`ParseErrorKind`, and the `format_position`/`format_traceback` rendering helpers. Reviewed by an Opus agent; **no correctness bugs and no panic paths found**. `cargo test`: 280/280 pass, of which 11 are `error::tests`. The substantive findings are all about *what the types can carry*: the error/diagnostic model is a `String` model, and the tolerant path is where that bites.)

**Summary:** The mechanics are right — Arc-based spans (self-contained errors, no `'src` infection, per §3.1), hand-written `Display`/`core::error::Error` (Decision 5), lazy `LineIndex` rendering with a graceful `None` fallback, provenance-chain walking. **1. The error model is stringly where the design doc says it should not be (API design) — `error.rs:214-224`.**
`ParseErrorKind` has exactly two variants: `Token(TokenErrorKind)` (structured) and `Syntax { message: String }` (a formatted sentence). Every parse-level condition in the crate goes through `Syntax`:

- `group_parser.rs:123` unclosed-at-EOF (carries: expected close delimiter)
- `group_parser.rs:137` mismatched/stray close (carries: expected close delimiter)
- `environment_parser.rs:253` terminator name mismatch (carries: expected name, found name)
- `environment_parser.rs:272` malformed terminator (carries: environment name)
- `environment_parser.rs:323, 338, 512, 539, 661` missing-terminator variants
- `argument_parsers.rs:235, 276, 361, 452` missing/malformed argument
- `nodes_parser.rs:430` unresolvable command

Each one `format!`s the very fields a consumer would want (`"missing terminator of environment ‘{}’: found the terminator of ‘{}’ instead"`, `environment_parser.rs:255-258`) into prose and then discards them. This is the same pattern DESIGN_RATIONALE §3.8 explicitly congratulates itself for *eliminating* at the token level: "structured `TokenErrorKind` (closed enum: end-of-stream-after-escape, forbidden-char — **replaces pylatexenc's stringly `error_type_info`**)". The parse level reintroduced it. The `#[non_exhaustive]` attribute and the doc comment ("parse-level conditions are added as the construct parsers grow, Phase 6.2–6.6") say the intent was to grow real variants — but 6.2–6.6 have landed and none were added; `Syntax` absorbed them all.

Consequence for the eventual consumers named in the goals (FLM, linters, editors/LSP): no error codes, no programmatic filtering, no "which environment?" without re-parsing the message. Localization is impossible. And the messages are constructed eagerly at the detection site even in strict mode, where nobody may ever read them.

Recommendation (this is a design decision for the user, not a mechanical fix): promote the recurring conditions to variants while `#[non_exhaustive]` still makes it cheap — e.g. `UnclosedGroup { expected_close: String }`, `TerminatorMismatch { expected: String, found: String }`, `MissingArgument { … }`, `UnresolvableCommand { name: String }` — and keep `Syntax` as the escape hatch for third-party construct parsers. The `Display` impl then owns the wording (one place, not 13), which is also where localization would hook in.

**2. The tolerant path is lossy because `Diagnostic` holds only a `String` — confirms the existing report's `engine/mod.rs:142` note, and locates the cause here (API design) — `error.rs:44-49`.**
`Diagnostic { severity, message: String, span }`. Strict mode returns `ParseError::new(kind, span)` with the kind intact; tolerant mode does `Diagnostic::error(kind.to_string(), span)` (`engine/mod.rs:142`). Verified: **that line is the only diagnostic producer in the entire library** (`grep 'diagnostics.push' src/` → one non-test hit). So *every* diagnostic a real parse produces is a severity + a sentence + a span, and even the one genuinely structured kind — `Token(TokenErrorKind)`, which is `Copy` and would cost nothing to store — is flattened.

The existing report calls this "not a bug today, consistent with the current `Diagnostic` type." Evaluating the error type's role in it, as asked: the loss is *caused* here, not in the engine. `ParseError` and `Diagnostic` are the same information under two policies (this is literally admitted by `ParseError::render`, `error.rs:268`, which rebuilds a `Diagnostic` from itself), yet only one of them is allowed to be structured. The minimal fix is an optional kind on `Diagnostic`:

```rust
pub struct Diagnostic<O: SourceOrigin = Option<String>> {
    severity: Severity,
    kind: Option<ParseErrorKind>,   // present for parser-reported conditions
    message: String,
    span: SourceSpan<O>,
}
```
with `Diagnostic::from_error_kind(kind, span)` doing the `to_string()` once. `engine::recover` then loses nothing, and `Diagnostics` gains a `filter_by_kind`. Combined with finding 1, this is the difference between "diagnostics you can print" and "diagnostics a tool can act on".

**3. One span per error; no related locations — and `format_traceback` has no producer (span/location plumbing) — `error.rs:311`, `error.rs:244-247`.**
`ParseError` and `Diagnostic` each carry exactly one `SourceSpan`. But several conditions are inherently two-location, and the code visibly struggles with the choice:
- `group_parser.rs:129` (unclosed at EOF) points at the **open** delimiter — so the message says "before end of input" while the caret is on `{`, nowhere near the end of input.
- `group_parser.rs:139` (stray close) points at the **close** — so the open brace, the thing the user actually needs to find, is not reported at all.
- `environment_parser.rs:329` points at the `\begin` trigger; `environment_parser.rs:343` points at the stray group close. Same split.

The idiom for this is a secondary/related span list (`rustc`'s "unclosed delimiter here", LSP's `relatedInformation`). ARCHITECTURE.md:782-784 anticipates exactly this — "open-blocks traceback — the existing `format_traceback` work slots in here" — and `format_traceback` (`error.rs:311`) is faithfully ported and tested. But **nothing produces its `&[(SourceSpan, String)]` argument**: `grep format_traceback src tests examples` → only `lib.rs:91` (the re-export) and this file's own tests. Nothing in the engine tracks open blocks, and neither `ParseError` nor `Diagnostic` has a field to hold them, so no rendered message can ever include a traceback. The helper is a rendering function for a data structure the error types don't have.

Recommendation: add `related: Vec<(SourceSpan<O>, String)>` (or a small `Note` struct) to `Diagnostic`/`ParseError`, have `render()` append `format_traceback(&self.related)`, and have the two-location sites populate it (the group parser already holds `self.open_span`; the environment parser already holds `self.trigger_span`). That wires the ported helper to a producer and fixes the "caret in the wrong place" cases in one move. This is the highest-value structural change in the file.

**4. `format_position` rebuilds a `LineIndex` on every call — rendering k diagnostics is O(k·N) (efficiency) — `error.rs:284-291`.**
```rust
let source = span.source();
let mut line_index = source.line_index();      // <-- fresh index, every call
let pos_str = match line_index.line_col(span.start()) { … };
```
`Source::line_index()` (`source/source.rs:137-140`) *constructs* a `LineIndex` (`line_starts: vec![0]`, `computed_end: 0`); `Source` caches nothing. `LineIndex::line_col` then lazily scans `content[0..byte_offset]` with `char_indices()` (`line_index.rs:97-110`). The laziness only pays off if the index is *kept*, and `format_position` drops it at the end of the expression.

Errors are cold, so per-error cost is fine — but the natural consumer of `Diagnostics` is "render all of them", and that is not cold: a tolerant lint of a 100 kB document with 500 diagnostics rescans an average of 50 kB per diagnostic ≈ 25 M char steps, and it is quadratic in document size. `format_traceback` (`error.rs:319`) has the same shape: one fresh index per open block, all over the same source.

Fix, in keeping with "no premature optimization" but not paying O(k·N) for the crate's own main rendering path: a renderer that owns one `LineIndex` per distinct source. E.g. `Diagnostics::render_all(&self) -> String` (or a small `DiagnosticRenderer` holding a `Vec<(Arc<Source>, LineIndex)>` matched by `Arc::ptr_eq`, mirroring the session's group-interior memo idiom), with `format_position` kept as the one-shot convenience. Note there is currently *no* API to render a `Diagnostics` collection at all — callers must loop — so the renderer would fill a real API gap and fix the complexity at the same time.

**5. The provenance walk duplicates `Source::provenance_chain()` (maintainability) — `error.rs:95-116` vs `source/source.rs:150, 326-340`.**
`Diagnostic::render` hand-rolls a `loop { match provenance { Primary => break, Resolved{..} => { …; provenance = triggered_at.source().provenance(); } … } }`. `Source::provenance_chain()` is exactly that traversal, already implemented as an `Iterator` (`ProvenanceChain`, `source.rs:326-340`) and separately tested (`source.rs:459`). `render` should be `for p in self.span.source().provenance_chain() { match p { Primary => {}, Resolved{..} => …, Synthesized{..} => … } }`. Two independent copies of the chain walk is the classic drift setup — and if the provenance enum grows a variant, only one of them is compiler-forced to handle it correctly (the hand-rolled loop *is* exhaustively matched today, so this is a duplication finding, not a bug).

**6. `Diagnostics` accumulation is unbounded, with no cap and no dedup (robustness) — `error.rs:130-143`.**
`Diagnostics` is a bare `Vec` with `push`. In tolerant mode every recoverable condition appends one `Diagnostic` — each ~48–56 bytes plus a heap `String` message (~40+ bytes) plus an `Arc` bump. Adversarial or merely degenerate input (a file of forbidden chars → one `ForbiddenChar` diagnostic per character, `nodes_parser.rs:499`) produces a diagnostic per input byte. A 10 MB input can therefore allocate on the order of a gigabyte of identical messages, in the exact mode (tolerant) that editors and linters — the stated consumers — are expected to use. Strict mode is immune (first error aborts).

Nothing here panics or is incorrect, and I would not gold-plate this; but a cheap `Recovery`-adjacent policy (e.g. `Diagnostics::with_limit(n)` where `push` beyond `n` increments a `suppressed: usize` counter, surfaced as "… and N more") is a few lines and turns an unbounded-memory failure mode into a bounded one. Worth a conscious decision rather than an accident.

**1. The peek-memoization contract cannot be honored as documented: `peek` receives `&ParsingState<L>`, not `&Arc<…>` (design / robustness) — `reader.rs:31-36`, `reader.rs:42`.**
The trait doc states: *"implementations may memoize on that key (states are immutable, so `Arc` pointer identity is a sound cache key)"*. But the signature is `fn peek(&mut self, state: &ParsingState<L>)`. A memoizing reader can only derive `state as *const ParsingState<L> as usize` from that reference — it cannot hold a strong reference to keep the allocation alive. The moment the engine drops that state (structural revert after a group/argument — `nodes_parser.rs:462-466`, `invocation_parser.rs:96-98` do exactly this), the allocator may hand the same address to the *next* derived state, and the reader serves a stale token for a different rule set. Every call site already has an `Arc`: `ParseContext::state` is `Arc<ParsingState<L>>` (`constructs/mod.rs:111`) and `cx.tokens.peek(&cx.state)` (`constructs/mod.rs:84`) only compiles today via deref coercion — so changing the parameter to `&Arc<ParsingState<L>>` would be source-compatible at every existing call site and would make the documented key actually attainable. ```

- **`paragraph_continues(content, end + 1, ws)` (`reader.rs:84`) is char-boundary and bounds safe**: `end` is the byte offset of the just-inspected `'\n'` (1 byte), so `end + 1 <= content.len()` and lands on a boundary.
- **`skip_whitespace` is O(run), not O(run²)**: a run containing ≥2 newlines breaks at the first one, so `paragraph_continues` (itself O(run)) runs at most once per call.
- **Detection priority matches the spec exactly** — paragraph break → expected group close → longest delimiter → command escape → comment start → specials scan → forbidden check → `Char` (`reader.rs:162-214`), identical to `rules.rs:105-108` and DESIGN_RATIONALE §3.2.
- **The `pre_space.end == span.start` adjacency invariant holds for every kind** (chars, commands, comments, group delimiters, `ParagraphBreak` at `reader.rs:250`, `EndOfStream` at `:168`). `TokenListReader::peek`'s `partition_point` + pre-space clipping (`list_reader.rs:69-72`) depends on exactly this, and the two readers agree.
- **The `enable_*` gates are correctly *conjunctive* in `detect_paragraph_break`** (`reader.rs:227-231`): whitespace off, multi-newline off, *or* `'\n'` not in `ws.chars` each independently suppress break detection — so a language that doesn't call newline whitespace gets `Char('\n')`, not a spurious break.
- **`GroupClose` under `enable_groups: false` + `expecting_group_close` stays resolvable**: the reader's expected-close-first-then-table priority (`reader.rs:265-276`) is mirrored exactly by `group_close_type` (`nodes_parser.rs:716-728`), so the class of a close emitted through the ungated expected-close path is re-derived consistently. The decided interaction (DESIGN_RATIONALE §3.2, interaction 1) holds end to end.
- The two `.expect("… checked above")` calls (`reader.rs:178`, `:312`) are genuinely unreachable (guarded by `pos < s.len()` / `name_start < s.len()` immediately above).
- Naming conforms to NAMING_STRATEGY (`TokenReader`/`StdTokenReader`, `CommandRule`, the command-not-macro terminology in all doc comments).

Harmless, but if they ever diverge the bug is invisible. **5. The recovery-placeholder token model is safe today, but the guard is out-of-band, not in the type (design note; answers the "are placeholders distinguishable?" question) — `error.rs:57-62`, `nodes_parser.rs:496-510`, `605-612`, `641-651`, `667-678`.**

**2. Every derivation deep-clones the whole `StateData` and rebuilds both caches — including for the transition that dominates the parse (efficiency / memory retention) — `parsing_state.rs:58-63`, `93-104`.**
`derived()` does `self.data.clone()` → `TokenRules::clone` (`rules.rs:203-220`) clones `whitespace.chars: String`, `groups: Vec<Arc<_>>`, `commands: Vec<CommandRule>` (each with its own `name_chars: String` — 52 bytes for a latexlike alphabet), `comments: Vec<CommentRule>` (a `String` each), `forbidden_chars: String`; `LibraryStack::clone` (`library/mod.rs:308-312`) clones the `Vec<Arc<dyn SpecLookup>>` *and* the `fallbacks: BTreeMap<CallableTypeId, Arc<dyn CallableSpec>>` (a real allocating map clone, for data that is set once at seeding and never changes). Then `freeze` rebuilds the `PrefixTable` from scratch — a `String` allocation per delimiter entry plus `first_chars` (`prefix_table.rs:60-101`) — and re-runs `L::specials_trigger_chars`. Order ~15–20 allocations per transition.

This is not a rare cost: derivation happens on **every group descent** (`group_parser.rs:98`, `environment_parser.rs:108` — memoized per `(base, rule)`, so siblings share, but every distinct base pays), on **every optional-argument probe** — `argument_parsers.rs:537` derives a fresh state to peek, *even when the optional argument turns out to be absent*, and that path is **not** memoized — and on every argument/slot with a `parsing_state_delta`. And because nodes record their parse-time state, each distinct state is retained for the lifetime of the tree: a large document holds N near-identical copies of the rules data (this is the same root cause as the engine review's memo-retention finding).

Worth noting that the doc's justification — "both derivations are cheap relative to a transition" (`parsing_state.rs:36-38`, echoed in DESIGN_RATIONALE §3.3) — is close to circular: the cache rebuild *is* a large fraction of the transition's cost. Two cheap, safe fixes:
- **Skip the `PrefixTable` rebuild when its inputs are unchanged.** It depends only on `(enable_groups, groups)`. The dominant transition — the group interior — overrides *only* `expecting_group_close` (`engine/mod.rs:103-106`), which is deliberately not an input (`rules.rs:164-167`). Holding it as `Arc<PrefixTable<L>>` and, after finalize, reusing the parent's `Arc` when `enable_groups` matches and the `groups` vecs are elementwise `Arc::ptr_eq`, is a pure win with no new trait bounds and no semantic change. Same applies to library-push deltas and ext-only deltas.
- **Make the rules data cheap to clone**: `Arc<str>` for `name_chars`/`whitespace.chars`/`forbidden_chars`, and `Arc` the `LibraryStack::fallbacks` map. That turns the `StateData` clone into a handful of refcount bumps and collapses the retention of N states to refcounts.

**3. `Lang::specials_trigger_chars` is called far more often than its doc implies (API cost / doc) — `parsing_state.rs:98-102`, doc at `lang.rs:186-194`.**
The hook doc says the filter is "computed when a state is frozen and cached on the state instance (rebuilt only at transitions, like the `PrefixTable`)", which reads as *rare*. In practice it runs once per group descent, per optional-argument probe, per argument delta. The hook's whole purpose is to let a preset derive trigger characters from the *library stack* (`specials.rs:5-16`, DESIGN_RATIONALE §3.3) — i.e. the natural implementation walks every library in scope. That is an O(#libraries × #specials) walk on every group descent. Unlike the prefix table (#2), there is **no** safe generic reuse rule here: the inputs include `L::StateExt`, which carries no `Eq` bound, so the state cannot tell whether they changed. Recommend documenting the per-transition cost expectation on the hook ("keep it O(small); cache the answer in an `Arc` inside `StateExt` if it is expensive to compute"), since a preset author reading the current wording will reasonably assume it runs a handful of times per parse.

**4. Interior mutability in `L::StateExt` would silently break the frozen-state contract — the one hole in an otherwise structural immutability guarantee (robustness / doc) — `lang.rs:101` + `parsing_state.rs:99`.**
`StateExt: Clone + Debug + Default + Send + Sync` does not exclude a `Mutex`/atomic. Because `ext()` hands out `&L::StateExt` from behind a shared `Arc<ParsingState>`, an interior-mutable ext can be mutated *after* the state is frozen, at which point (a) `trigger_chars` — computed from the **whole** `StateData`, ext included (line 99) — is stale, (b) the `TokenReader` contract "peek is idempotent per (position, state *instance*), implementations may memoize on `Arc` pointer identity" (`reader.rs:31-36`) is violated, and (c) the engine's `(base, rule)` ptr-keyed memo can serve an interior state whose ext has since changed. This is not a live bug (no in-tree `Lang` does it), but ARCHITECTURE.md §nodes explicitly *sanctions* "interior-mutable set-once types" as the idiom for `NodeExt`, so a preset author could plausibly carry the idiom over to `StateExt`. One prohibiting sentence in the `StateExt` doc (and/or on `ParsingState`) closes it.

**5. `impl Clone for ParsingState` is dead code and the only identity hazard in the file (API design) — `parsing_state.rs:130-138`.**

**1.** *(fixed July 2026 — contract documented on `TokenRecovery::resume_pos` and referenced from `resume_at`; the content loop's recovery arm now aborts with the token error, even in tolerant mode, when the reader did not advance. Pinned by a violating-reader test.)*

**2. `resume_at` routes around the readers' own positional guards; `TokenReader` has no positional move (API design / robustness) — `constructs/mod.rs:70-74`.**
The doc is candid that "go to `pos`" is *phrased* as a zero-width marker token, but two consequences deserve to be visible:
- `StdTokenReader::move_to_pos` (`reader.rs:141-145`) `debug_assert!`s `pos <= content.len()` **and** `content.is_char_boundary(pos)`. `resume_at` never reaches it: it calls the *trait* method `move_to`, which is a bare `self.pos = tok.span.start` (`reader.rs:394-399`). So a bogus `resume_pos` from a third-party reader lands the position mid-`char` or past the end with no diagnosis, and the next `peek` slices `content[pos..]` in `skip_whitespace` (`reader.rs:79`) — a lib-code panic, exactly what CLAUDE.md forbids.
- The marker trick silently adds an **unstated implementor contract**: `move_to` must be computed from the token's spans, never from token identity or list membership (a reader that looked the token up in its own list would be handed a synthetic token it has never seen). `StdTokenReader` and `TokenListReader` both comply — and both already carry an inherent `move_to_pos` (`reader.rs:141`, `list_reader.rs:64`) that the trait cannot reach.

Recommended: add `fn move_to_pos(&mut self, pos: usize)` to `TokenReader` (default body = today's marker trick, so no implementor breaks), let the two readers keep their guards, and reduce `resume_at` to a forwarding call — or delete it in favor of the trait method.

**3. The helpers are `pub(crate)`, but the protocols they encode are obligations of *public* extension points (API gap) — `constructs/mod.rs:70`, `constructs/mod.rs:81`.**
`ArgumentParser` is a public trait (`spec/structure.rs:87`) whose docs *require* implementors to follow two protocols this file owns: "absent means nothing was consumed — the reader is rewound past any probed noise" (`structure.rs:96-104`) and, per the 6.5 ruling, "token error while probing → absent without diagnosing (tolerant) / abort (strict)". An out-of-crate implementor gets `scan_argument_noise`, `stage_pre_space` and `ArgumentNoise::rewind` (all `pub`), but **not** `try_peek` and **not** `resume_at` — so a custom argument parser (or a `make_invocation_parser` takeover parser doing `\verb`-style repositioning) must re-derive both the recovery-policy peek and the marker-token trick from scratch, and any divergence produces exactly the double-report the design set out to avoid. Both helpers are already documented as protocol rather than as implementation detail; make them `pub` (and re-export them alongside `scan_argument_noise`), or fold them into the public surface some other way.

**4. The `cx.state` swap/restore protocol is hand-rolled at seven sites and belongs on `ParseContext` (API design / maintainability) — `constructs/mod.rs:100-115`.**
Every parser that scopes a child state repeats the same three-step dance, and each one must remember to restore **before** the `?`:

| site | what is scoped |
|---|---|
| `nodes_parser.rs:462-466` | invocation descent |
| `nodes_parser.rs:697-701` | group descent |
| `group_parser.rs:110-114` | group interior |
| `invocation_parser.rs:96-99` | per-argument delta |
| `argument_parsers.rs:538-541` | the optional-argument **probe peek** |
| `argument_parsers.rs:579-582` | optional-argument contents |
| `environment_parser.rs:109-112` | rigid name group interior |

All seven are correct today (each restores before propagating), but the correctness is per-site discipline, and `argument_parsers.rs:539-541` shows how unnatural it gets: `let open = try_peek(cx); cx.state = Arc::clone(&argument_state); match open? {…}` — a `Result` deliberately held un-`?`-ed across a restore. A scoping accessor on the context makes the ordering unrepresentable:

which type-checks for all seven (the closure reborrows `&mut self`, and `f` may capture the child parser mutably). **1. The seam has no consumer, and the trait doc asserts a wiring that does not exist (documentation accuracy / design-note) — `resolver.rs:22-24`.**

But the trait doc states: *"The parser is generic over the resolver; [`NoResolver`] is the zero-sized, zero-cost default for builds that must not perform any lookup or I/O."* It is not: `ParserSession` (`engine/mod.rs`) has no resolver field and no type parameter for one; per `ARCHITECTURE.md:734` the resolver is to live on `Language<L>`, which `ARCHITECTURE.md:744-747` explicitly **defers to Phase 7 at the earliest**. **2. `SourceResolver` is the only extension trait that missed the July 2026 `Send + Sync` sweep (design / API stability — highest priority) — `resolver.rs:25`.**
DESIGN_RATIONALE.md:703-709 ("Thread safety is a core contract") enumerates the traits that gained `Send + Sync` supertraits: `CallableSpec`, `SpecLookup`, `ArgumentParser`, plus the `Lang` associated types and `SourceOrigin` (`origin.rs:26` — *"`Send + Sync` because sources are `Arc`-shared"*). `SourceResolver` is declared with no supertraits at all. That looks like an oversight rather than a decision, and the rationale's own argument applies to it verbatim:
- **It is stored in the shared, long-lived object.** `ARCHITECTURE.md:734` puts the resolver in `Language<L>`'s field list, and the ownership model (`ARCHITECTURE.md:770-773`) has `ParserSession<'env>` *borrow* the `Language` — so the stated goal "share preset libraries across parallel parses" requires `Language<L>: Sync`, which requires `R: Sync`.
- **It is the trait most likely to hold non-`Sync` state.** The rationale's own worked example for `SpecLookup` — "a database-backed lookup holds `Mutex<Connection>` (forced by `&self` anyway)" — describes a *resolver* even more exactly: file caches, HTTP clients, DB handles. And `resolve(&self, …)` already forces interior mutability for any caching resolver, so the bound "never introduces a wrapper, it only selects `Mutex` over `RefCell`".
- **The migration direction is one-way.** Quoting the same entry: *"the reverse migration (adding bounds later) would break implementors holding non-`Send` state, which is why the bounds land now while the API is fluid."*
Recommend `pub trait SourceResolver<O: SourceOrigin = Option<String>>: Send + Sync`, or — if the exclusion is deliberate (e.g. "the resolver is per-session, never shared") — record that explicitly in DESIGN_RATIONALE §3.1, because as it stands the file silently contradicts a documented crate-wide contract. (`ResolveError` is already `Send + Sync` by construction: two `String`s.)

**3. No recursion guard, and the trait contract does not say whose job it is (robustness / design) — `resolver.rs:25-32`.**
Verified by probe: with `MapResolver` mapping `a.tex` → `\input{a.tex}`, `resolve("a.tex", …)` succeeds every time, minting a *fresh* `Source` per call (fresh content clone, provenance chain one hop longer). Once #1 is wired, a self- or mutually-including document is an unbounded parse — growing memory plus recursion depth in the construct parsers — with no diagnostic. This is **not** an `Arc` cycle (a `triggered_at` always points into an *older* source, so the provenance graph stays a tree, exactly as `source.rs:286-289` promises); it is plain non-termination, which the structural-acyclicity argument does not address.

The good news: the information needed is already reachable from the arguments. I confirmed that `triggered_at.source().provenance_chain()` (`source.rs:150`) enumerates every enclosing `Resolved { reference }`, so a resolver *can* detect re-entry today with public API. What's missing is a decision and a sentence:
- either the (future) session enforces a max include depth and diagnoses on exceed — my preference, since it is policy, not I/O;
- or the trait contract states that implementors must detect re-entry, in which case ship the helper here (e.g. `pub fn resolution_depth(triggered_at: &SourceSpan<O>) -> usize` / `pub fn is_being_resolved(triggered_at: &SourceSpan<O>, reference: &str) -> bool`).
Note the reference string is not a canonical identity (`./a.tex` vs `a.tex` vs a symlink), so a *guaranteed* cycle check needs the embedder's canonicalization — which is an argument for a depth limit at the session (cheap, always correct as a backstop) *plus* the chain-walk helper for embedders that can canonicalize. **4. The `Arc<Source>` return type invites caching, but a cached source carries a stale `triggered_at` (contract gap / design) — `resolver.rs:27-31`, `113-117`.**
`resolve` returns `Arc<Source<O>>`, so a resolver may legally return the *same* `Arc` for a reference included twice — an obvious optimization for a shared preamble, and the type signature actively suggests it. But provenance lives **on the `Source`** (the deliberate March/July decision, DESIGN_RATIONALE.md:150-156: "one hop per source, not per location"), so a shared source records only the *first* trigger site, and every diagnostic inside the second inclusion would be rendered as "included from «the first `\input`»". Silently wrong include chains, no panic, no test would notice. `MapResolver` gets it right (fresh `Source` per call, `resolver.rs:113-117`), but nothing in the trait doc forbids the shortcut and nothing detects it. Fix: state the contract on `SourceResolver::resolve` ("must return a source whose provenance records *this* `triggered_at`; sharing one `Arc<Source>` across include sites loses the include chain"), and, at the future call site, `debug_assert!(matches!(src.provenance().triggered_at(), Some(t) if t == triggered_at))`.
The flip side is a genuine cost worth naming in the same doc: because provenance is per-source, **content is necessarily duplicated per include site** — `MapResolver::resolve` does `content.clone()` (`resolver.rs:114`), a full copy of the file on every resolve, forced by `Source`'s `content: String` (`source.rs:23`). Not urgent; worth one line of doc so nobody "optimizes" it via #4's trap.

**5. `ResolveError` cannot carry a cause — the primary intended implementor is a file reader, and it must stringify its `io::Error` (API design) — `resolver.rs:34-64`.**
The whole point of the module header (`resolver.rs:3-5`) and of DESIGN_RATIONALE §3.9 is that the embedder brings the I/O. Every such implementor therefore *has* a structured error — `io::Error`, an HTTP status, a DB error — and this type gives it exactly two `String`s and no `Error::source()` override (`resolver.rs:64` takes the default). So the cause is flattened into prose at the boundary and cannot be recovered downstream (no `ErrorKind::NotFound` vs `PermissionDenied` discrimination). `core::error::Error` is already imported and `alloc::boxed::Box` is available, so a dep-free fix exists: an optional `cause: Option<Box<dyn core::error::Error + Send + Sync + 'static>>` plus `fn source(&self)`. Related and also missing: there is **no bridge from `ResolveError` into `ParseErrorKind` / `Diagnostic`** (`error.rs` has no resolve variant), so the wiring in #1 will have to decide — probably at the same time — whether a failed `\input` is diagnose-and-continue (tolerant) or an abort (strict), i.e. it is a `Recovery`-policy question. **6. The `LineIndex`-per-`format_position` cost is amplified here, but the cache does *not* belong in this file (efficiency — direct answer to the review question) — `error.rs:284-291`, `error.rs:90-116`.**
Confirmed by reading the code: `format_position` (`error.rs:283-291`) calls `source.line_index()`, which constructs a brand-new `LineIndex` (`source.rs:137-140`) that re-scans from byte 0; and `Diagnostic::render` calls it **once for the diagnostic plus once per provenance hop** (`error.rs:93`, `102`, `110`). So this file's output makes the existing problem *multiplicative*: rendering k diagnostics inside a d-deep include chain rescans the ancestor documents k·d times, and the parent document — typically the largest — is rescanned once per diagnostic in every included file.

Nevertheless the cache does not belong at the resolver seam, for three concrete reasons: a resolver is consulted only at source **creation** time and never at render time; `NoResolver` is a ZST that must stay one; and sources created by `Source::new` (the common case — the primary document) never touch a resolver at all, so a resolver-side cache would cover exactly the sources that need it *least*. The two real homes:
- **On `Source`** — blocked dep-free. A cache field needs `Sync` interior mutability; `alloc` has no `Mutex` and `core` has no `OnceLock`, `OnceCell` would cost `Sync` (already the recorded reason in DESIGN_RATIONALE.md:542 / §3.3), and `spin` is a new dependency that §3.9's zero-dependency policy forbids.
- **In the renderer (`error.rs`) — recommended.** A `Diagnostics::render_all(&'a [Diagnostic<O>])` (or a small `PositionFormatter<'a>`) holding `Vec<(*const Source<O>, LineIndex<'a>)>` keyed by `Arc::as_ptr(span.source())`: dep-free, borrows the sources it renders so `LineIndex<'c>`'s lifetime works out, reuses `LineIndex`'s existing lazy extension across all positions in a source, and is the same pointer-keyed-memo idiom already blessed in `ParserSession::group_interior_state` (`engine/mod.rs:53-54`). Route the fix through `error.rs`; nothing changes in `resolver.rs`.

**1. `scan_specials`' doc states no obligations on `SpecialsMatch::end` — the three malformed values give an infinite loop, a release panic, and a reversed span (robustness / documentation) — `lang.rs:176-183`, cross-check `specials.rs:31-32`, `reader.rs:190-201`.**
The reader consumes the returned `end` unvalidated: `Span::new(pos, m.end)` (`reader.rs:198`). Three failure modes, all reachable from a plain `Lang` bug:
- `end == pos` → a zero-width `Specials` token. `StdTokenReader::move_past` sets `pos = tok.span.end` (`reader.rs:386-392`), and the dispatch arm consumes the trigger whole (`nodes_parser.rs:459`), so the reader never advances → the content loop spins forever.
- `end > content.len()` or `end` off a char boundary → the *next* `peek` panics in `skip_whitespace` (`content[pos..]`, `reader.rs:78`), and the staged `SourceSpan` panics on resolution.
- `end < pos` → `debug_assert!(start <= end)` in `Span::new` (`span.rs:23`); in release, a reversed span propagates.

The `SpecialsMatch::end` doc says only "Byte offset one past the end of the matched trigger". The hook doc says only "Positions are absolute byte offsets into `content`". Neither states the invariant `pos < end <= content.len()`, `content.is_char_boundary(end)`, nor that `name` should be `&content[pos..end]` (the reader records `name` and `span` independently — a hook may return a name that does not match its own span, and nothing checks it). Since this is *the* hot-path hook a preset must implement, spell the obligations in the rustdoc; the reader-side validation (a `debug_assert!` plus treating a malformed match as "no match") was already recommended in the reader review and would make the contract enforceable rather than merely stated. (Note the prior reader.rs finding and this one are the same defect seen from the two sides; the trait doc is the cheaper place to fix it.)

**2. The error path of `scan_specials` is under-specified: an error without a recovery token aborts *even in tolerant mode*, and a recovery that doesn't advance loops forever (documentation / test-coverage) — `lang.rs:170-171`, cross-check `nodes_parser.rs:496-510`.**

**1. But the central preset extension pattern documented in the architecture *requires exactly that downcast*: `Lang::finalize_node`'s docs (`state/lang.rs:234-236`) say "A preset dispatches to spec-specific behavior itself (match a `Callable`, read its `spec`, **downcast**, attach ext)", and DESIGN_RATIONALE.md:1135-1139 makes the same promise ("FLM's `Lang` sees a `Callable`, reads `data.spec`, downcasts to its own spec trait, attaches its `flm_specinfo`-like ext") — it is the stated reason the core needs *no* spec-level finalize hook. The crate's own rehearsal test concedes it — `nodes_parser.rs:2013-2016`: *"a preset would downcast `data.spec` to its own spec trait; the test derives from the invocation facts and the spec's declarative surface"*, i.e. the documented pattern is untested because it is unimplementable outside the core. `Arc<dyn CallableSpec<L>>` already implies `'static`, so adding `+ core::any::Any` to the supertraits costs implementors nothing and enables `downcast_ref::<ConcreteSpec>()`. (Downcasting *trait object → other trait object* — "its own spec trait" — needs more than `Any`; if that is really the intent, a preset-facing hook is needed instead.) This is a design decision, so per CLAUDE.md rule 1 it should go to the user — but it is the highest-signal gap in the file, and it is also the blocker for #4.

**2. `StdCallableSpec` accepts slots its own default factory cannot parse (robustness / ergonomics trap) — `callable.rs:49-51`, `86-87`, vs `invocation_parser.rs:136-141`.** The trait doc at `callable.rs:48-49` explicitly invites the declaration — "an environment-shaped callable has exactly one (its body)" — and `StdCallableSpec::new(arguments, slots)` (`callable.rs:91-96`) takes a slot `Vec`. ```
So the natural user action — `StdCallableSpec::new(args, vec![Arc::new(SlotSpec::new())])` — yields a spec that **panics in debug builds and silently drops the body in release**. The crate's own spec test builds precisely that shape (`spec/mod.rs:86-93`, `vec![Arc::new(SlotSpec::new().named("body"))]`, "with a body slot for good measure") — harmless there only because it never parses. **2. Brace protection silently fails when the option's delimiters are *also* a group class in the argument state (correctness — latent design gap) — `argument_parsers.rs:531-532`, `565-572`.**
The revert-to-`argument_state` half of the rule protects `]` **only because `]` is an ordinary character in that state**. The parser's own comment (`argument_parsers.rs:471-473`) says the minted rule is "prepended so it wins ties against a same-spelling rule already in scope" — i.e. a preset that registers `[`…`]` as a real group class is an anticipated configuration (and `nodes_parser.rs:2436-2442` builds exactly such a rules set for its own `Compute` test). In that configuration the flagship guarantee breaks. Measured, with `[`/`]` added to the base `TokenRules::groups` as a *separate* `Arc`:

```
\item[{a]b}]  →  Tolerant: diagnostic "unclosed group: expected ‘}’",
                 root loop stops with UnexpectedGroupClose{10..11}   (mangled)
\item[a]      →  clean                                               (unaffected)
```

Why: inside the brace group the base state is `argument_state`, whose rules now *do* carry a bracket class, so the `]` tokenizes as a `GroupClose` with no matching open → decision-8 unwinding → the `}` escapes. The revert target needs to be a state where the option's **close delimiter is neutralized**, not merely the pre-mint state. Note this is *not* covered by the planned "temporary group rules, stripped in the derivation path" mechanism (DESIGN_RATIONALE §3.6, *Revisit*): stripping removes the *temporary* rule, while the offending rule here is a permanent one. Recommend at minimum recording the precondition ("the minted close delimiter must not be a group delimiter of the argument state, or brace protection degrades to unwinding") on `OptionalGroupArgumentParser` and in §3.6; the alternative (make the revert state suppress the close spelling) is a design call.

**3. Every optional argument misses the group-interior memo *and* permanently grows it — but the minted `Arc<GroupRule>` is not the culprit (efficiency) — `child_state.rs:23-25` vs `argument_parsers.rs:537`, `engine/mod.rs:98-126`.**
Correcting the hypothesis first: the rule is **not** minted per use — `OptionalGroupArgumentParser::rule` (`argument_parsers.rs:496`) lives inside the `ArgumentSpec` (tier 1, `Arc`-shared), so the same `Arc<GroupRule>` is handed to every occurrence, and it is a *good* memo key. Result: a guaranteed memo miss plus one permanently-retained entry, per optional argument.

Measured (instrumented `ParsingState::derived` + a `memo_len()` accessor in the scratchpad copy):

| input | `derived()` calls | memo entries |
|---|---|---|
| `\item[a]` | 2 | 1 |
| `\item x` (argument **absent**) | **1** | 0 |
| `\item[a]\item[b]\item[c]\item[d]` | 8 | **4** |
| `{a}{b}{c}{d}` (four sibling brace groups) | **1** | 1 |
| `\item[a[b[c[d]]]]` | 5 | 4 |

Each `derived()` is a full `StateData` clone + eager `PrefixTable` **and** `TriggerChars` rebuild + `finalize_transition` (`parsing_state.rs:32-38, 58-63`), on top of the per-occurrence `Vec<Arc<GroupRule>>` clone at `argument_parsers.rs:531-532`. Note the third row: **an absent optional argument still pays a full state derivation** for the probe, which is then thrown away — and `\item` with an absent option is the common case in real documents. And every entry added at `engine/mod.rs:116-120` enlarges the linearly-scanned memo (`engine/mod.rs:107-111`, already flagged as O(n²) in the engine review) for the rest of the parse, so N optional arguments cost O(N) retained states *and* lengthen the scan of every subsequent group descent anywhere in the document. This is the concrete profile that DESIGN_RATIONALE's "a `(base, Arc<ArgumentSpec<L>>)`-keyed entry kind is a possible 6.4+ extension, strictly profiling-driven" was waiting for.

Suggested fix: a second narrowly-typed keyed helper on the session for the minted-contents derivation — the key `(base, Arc<GroupRule>)` has `Arc` identity exactly like `group_interior_state`'s, since `self.rule` is spec-held and `argument_state` is a plain `Arc::clone` of the loop state whenever the spec carries no `parsing_state_delta` (`invocation_parser.rs:92-95`). That collapses the four-`\item` case from 8 derivations/4 entries to 2/1, and makes the group-interior memo hit as a side effect. (Caveat: if the argument spec *does* carry a delta, `argument_state` is itself freshly derived per invocation, so the chain only closes if the `(base, spec)` argument-state memo lands too.)

Worth stating clearly: `child_state.rs:23-25`'s decided semantics 4 ("`Arc` in, `Arc` out … preserves pointer identity, which keeps identity-keyed memoization sound") **is upheld** by the policy code at both descent sites. The identity loss happens upstream of the policy, at the state-minting site.
