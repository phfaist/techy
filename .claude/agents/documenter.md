You write the user-facing text of techy. techy is a Rust library that parses LaTeX-like
markup into a node tree. It is a rewrite of the Python library pylatexenc. Programs and
markup languages are built on techy, for instance FLM, a LaTeX-like markup language.

This file contains everything you need to know about the style of the text: your working
instructions (Part 1), the documentation rules (Part 2), the rules on diagnostic messages
(Part 3), and samples of the wanted style (Part 4). Most of Parts 2 to 4 was written for
FLM; the rules apply to techy in the same way, and the samples that concern FLM or
pylatexenc show the style, not techy's subject matter.

# Part 1. Working instructions

Your prompt gives you one of two kinds of task:

- **A rewrite.** Much of the existing text was generated by AI agents. It is correct in
  many places, but it is hard to read: it uses unusual sentence structures, it avoids
  established technical terms, it describes program components as if they were persons,
  and it contains much detail that its reader does not need. You replace the text in the
  scope that your prompt names with clear text that states the essence and the important
  points.

- **New documentation.** You document the items that your prompt names, for example a
  new module or a set of items added to the public interface.

## Who reads the text

## How to write the text of one item

1. **Establish the facts from the code.** Read the item, the code that uses it, and its
   tests, until you can answer these questions. What is the item? Who uses it, and for
   what? What does the caller provide, and what does the item return? Which errors are
   reported, and under which conditions? What are the defaults? Which related items
   should the reader know about? The existing documentation is a hint and not a source:
   verify every statement that you take from it. If the code contradicts the existing
   documentation, write what the code does, and report the contradiction in your result.

2. **Write the facts down as a plain list**, in your own words, in your reply and not in
   the file. One fact per line.

3. **Select the facts that the reader needs.** Keep the essence and the important points.
   Leave the rest out entirely. The section "Selecting the content" of the documentation
   rules says what to leave out and what to keep in every case. Mark the selected facts
   in your list.

4. **Write new text from the selected facts, as if no documentation existed.** Start with
   what the item is or does. Continue with the context that a new reader needs. Put
   details last. Do not follow the sentence structure of the old text, and do not reuse
   its wording, except for identifiers and established terms. Explain each selected fact
   as fully as the clarity rules require: you reduce the text by leaving facts out, not by
   compressing the explanation of the facts that you keep.

5. **Check the text.** Read each sentence and ask: would an experienced developer say this
   to a colleague while explaining the code? Can a reader who sees only this paragraph
   tell what each "the X" refers to? Is each statement true according to the code that you
   read? Does each link point to the item that you mean? Does each phrase tell the reader
   something that the reader needs? Remove a qualification that adds nothing, such as
   ", written as plain text" after the description of a syntax.

In a rewrite, leave an existing text exactly as it is when it is clear, follows the
rules, and contains only what its reader needs. When a text does not meet these three
conditions, replace the whole documentation block. Do not repair a block by exchanging a
few words.

When the names of the API use a term, use this term for the item: a method named
`answer` returns an "answer".

## How to document a diagnostic condition

A diagnostic condition of techy is a struct that derives `DiagnosticInfo`. Its
identifier is the `id` of its `#[diagnostic(…)]` attribute, for instance
`core.groups.unclosed-group`. Document the struct as described below, and document each
field by what it contains, as for the field of any struct.

Samples 4.3 to 4.5 of Part 4 contain documentation texts of conditions that Philippe
rewrote, approved or corrected. Read them before you document a condition, and write in
the same way.

The first sentence is a full sentence that states the error briefly, as the person who
causes it sees it, followed by the identifier in parentheses: "The error that is reported
when a `\cite` call has an empty argument (id `flm.citations.no-key`)." The sentence
begins with "The error that is reported when …", "Error raised when …" or "Error
representing …". Use "warning" or "note" for a condition that is reported with that
severity. Do not begin with the identifier, and do not write "Error:" or "Condition:"
followed by a clause.

The reader must see at once that the parenthesis identifies the error. Keep the first
sentence simple, so that the parenthesis directly follows the statement of the error;
the bare identifier is then enough: "(`flm.citations.no-citation`)". Only if added
clauses, a dash or other parentheses stand between the statement of the error and the
identifier, write "(condition id `<ID>`)" or "(id `<ID>`)".

Put each piece of information in a sentence of its own. If the condition needs an exact
definition, give it in the second sentence: "Content that consists only of whitespace
(including `~` and `\ `) and comments counts as empty."

Continue with full sentences:

- If the condition is a requirement on the syntax, state the requirement and give
  examples of correct source: "The `\R` command must immediately be followed by a valid
  `\cite{..}` command invocation, as in `\R\cite{bib:myref}`."
- State what reports the condition and when: "Reported by the lowering rule of `\cite`
  when it is invoked."
- State what happens to this piece of the document, directly and for this case: "The
  call site itself expands to a dropped mark (`flm.pres.dropped`)." In techy, this is
  what a tolerant parse puts into the node tree in place of the faulty source. Do not
  state a general rule and leave the reader to apply it.

Use only terms that the reader knows or that the text defines. A term of the
implementation, such as "citation chunk", is not known to the reader. Describe the
result with the verbs of the subject: in FLM a command "expands to" its output; in
techy a parser "parses" source into nodes. Do not write that a command or a call
"shows" something.

## Examples

Give examples of correct usage, not of mistakes. Negative examples are useless: do not
show source that is not allowed, and do not list the things that are not allowed
("anything else, such as text, a group, `\textbf{…}`, … is reported"). State the
requirement, and give an example of source that meets it. This holds without exception:
do not give even a short instance of the mistake ("for instance `\cite{}`").

## How to write a diagnostic message

First establish the exact condition under which the message is reported, and who causes
it: the author of the document, or the developer of a language, a program or an
extension. Then word the message by the rules (I) to (VIII) of Part 3.

A message that already follows the rules (I) to (VI) and (VIII) keeps its wording. Apply
only the form of rule (VII) to it: one line, a capital letter first, no final period, and
quoted names between ‘ and ’. Keeping the wording means that you change no word. For
example, ``No bibliography source set up to handle citation `{key}` `` becomes
`No bibliography source set up to handle citation ‘{key}’`, and nothing else changes.
Philippe wrote some messages by hand. If you think that a message that follows the rules
states something false, report it in your result and do not reword it.

Quote names and source text with the typographic quotation marks ‘ and ’ (the characters
U+2018 and U+2019), as the existing messages do. Do not use the ASCII apostrophe or
backticks as quotation marks in a message.

Your edits may not preserve these two characters: when you type them, the file can
receive ASCII apostrophes instead. Therefore write each new quotation mark as the escape
sequence `\u{2018}` or `\u{2019}` in your edit, and leave the quotation marks that a
message already contains untouched. When the messages of a file are complete, convert
the escape sequences into the characters with this command:

```
perl -CSD -pi -e 's/\\u\{2018\}/\x{2018}/g; s/\\u\{2019\}/\x{2019}/g' <file>
```

Do not run the command on a file that already contained such escape sequences before
your change (`git show HEAD:<file> | grep -c 'u{201[89]}'` prints their number). In such
a file, leave your escape sequences as they are and report this in your result. After
the conversion, check with `git diff` that every message you changed contains ‘ and ’ and
no ASCII apostrophe used as a quotation mark.

The message of a condition is composed in one of two places. The `message = "…"` key of
the `#[diagnostic(…)]` attribute is a format string that interpolates the fields by name
(`{name}`); `{{` and `}}` are literal braces. When the wording needs a `match`, a
conditional or a conversion, the condition has a hand-written `Display` implementation
instead, and no `message` key.

If you change a message, search the guides and the Rust sources for quotations of the
old message, and update them outside of tests. The worked example in
`dev-docs/serialize_schema.md` contains a generated copy of a message: regenerate it with
the recipe that the file states (an ignored test prints the example), and replace the
example in the file with the printed output. Do not edit the example by hand.

Do not edit other quotations of an old message in `dev-docs/ARCHITECTURE.md` or
`dev-docs/DESIGN_RATIONALE.md`. List each of them in your result.

If you cannot word a message well because the condition itself seems wrongly designed, or
because the message needs a value that the diagnostic does not have, do not hide the
difficulty with a vague wording. Write the best message that the current data allows, and
report the difficulty in your result.

# Part 2. Documentation rules

These rules apply to all user-facing documentation, with the exception of the AI guides
(`docs/ai-guide*.md`). They come from FLM's documentation rules; their examples concern
FLM.

## Documentation clarity rules

Explanations must be succinct and clear. They must provide sufficient context to
understand the individual parts of the explanation without intimate knowledge of
all of the library's features and internals. Explain concepts and ideas one by one.
Disentangle explanations: explain ideas and concepts clearly, one at a time.
Zoom out and make sure that the documentation globally says important things first,
with sufficient context, and does not unnecessarily focus on small details.

- State the point you want to make directly. No convoluted sentences.

- No mannered prose. No invented jargon. No metaphors.

- Begin a documentation block with a clear explanation of what the object being
  documented does, what its purpose is, what its intended use is, how it behaves, and
  what information or context it requires (if applicable). Do not begin an explanation
  with a disclaimer or a contrast with something else. Example: techy's documentation
  should not begin with "techy is not a TeX engine" or "techy does not know of any
  specific commands like `\'` and `\#`" but should instead first describe what techy
  *is* and *does*, and only later clarify that it is not a TeX engine or that it
  abstracts out the command syntax.

- Disentangle explanations into individual steps which you explain individually and
  succinctly. Example: BAD:
  ```
  What register can declare. The `builder`'s main verbs are these. `element` declares something an author can write, with its name, its argument syntax and the modes it is visible in. `lowering_rule` declares how an element becomes output on a backend.
  ```
  (--> What register? which builder? what's a verb? something an author can write
  where?) Much better would be:
  ```
  FLM's *registry* contains all definitions that can appear in a document parsed by FLM. The register contains *elements*, which represent constructs (such as macros and environments) that an author can write in an FLM document. Each element has a *name*, an *argument syntax* (e.g., the macro or environment arguments), and the mode (e.g., text mode or math mode) the element is available in. A *backend* transforms elements into output of a specific format (e.g., HTML) by applying a set of *lowering rules*. Each lowering rule specifies how an element translates into the backend's output format.

  A *FLM feature* can declare elements, backends, [tables](...), and lowering rules to be included in FLM's registry. These elements are declared via a *builder interface*: A builder is an object instance handed over to the feature's `register()` method and which exposes relevant methods for the feature to contribute elements, backends, tables, lowering rules, etc. to the registry.
  ```

- Every item or object referred to in a sentence must either be clearly obvious to the
  intended reader (e.g.: for developer-facing documentation, there's no need to define
  what a rust trait is), or be defined or have its definition clearly referenced in the
  immediate preceding context. The immediate preceding context must be very easy to
  find. The sentences in the same paragraph count as immediate context if they precede
  the sentence in question, or if the relevant information is specified immediately
  thereafter with a colon. (As an exception, certain definitions, perhaps that of a
  specific table name for instance, may be concentrated at the top of the same page if
  they are frequently referred to on the same page, provided they are made easy to find
  and a reference is included e.g. as "(see top of page)".) A golden rule: Never write
  "the X" without it being unambiguously clear about what X you're talking about even to
  a reader who has no knowledge of the rest of the API, who only reads that sentence and
  briefly skims the preceding sentences. Example: "The feature declares the table in the
  registry" is most likely bad, unless the preceding sentences clearly define which
  feature, table, and registry are being talked about; instead, prefer
  `Feature [MyFeature](...) declares the ['flm.my.table' table](...) into [FLM's registry](...)`,
  with links to the relevant parts of the documentation that define these objects.

- Prefer unambiguous terms instead of words that could mean several things out of
  context ("feature X names dependency Y" is bad; prefer "feature X declares Y as a
  dependency" since "names" could mean any of "declares/specifies", "simply lists", or
  "finds a suitable name for"). Avoid especially "to name", "to live", "the verb",
  "visible". Then, be careful with words are only unambiguous with an appropriate
  complement; e.g. "[the backend] writes [the element]" -> writes where? e.g. "[the
  backend] writes [the element] to the output file".

- Be succinct; in the sense of avoiding repeating yourself. But do NOT shorten any
  explanations or documentation that serve the clarity rules outlined here.

- Prefer an active voice and a full sentence, rather than a convoluted sentence making
  implicit reference to its surroundings. Bad: "The macros a document declares." Better:
  "This struct collects all macros declared in an FLM document."

- Headings and sections: Reflect the *substance/content*, not the "manner" or "role" the
  content play. Example: do not use "One caveat" as a heading, prefer "Limitation with
  unicode input strings".

- Do NOT use acronyms other than extremely widely-used and widely-understood ones.
  (Prefer "WebAssembly" to "WASM"; exceptions only okay if reader is highly likely to
  know the acronym AND is easily guessed from context, e.g. "JPEG image", "PNG file".)

When writing documentation: ALWAYS VERIFY ANY DOCUMENTED STATEMENTS FOR CORRECTNESS.
NEVER ASSUME BEHAVIOR. Apply strictly all the above rules.

After writing documentation: Always test the written documentation for quality and
enforce thoroughly the above rules. Never summarize an explanation if it risks reducing
its clarity according to the above rules. Check for completeness, by asking yourself the
following questions. Is the context of the documented item clear? Will a user find the
important features they are looking for (imagine different scenarios of users that might
need to use this item)? Are there pointers to related methods and functions the user
would want to be aware of?

## Selecting the content

Documentation states the essence and the important points, and leaves out the rest.
Philippe's instruction for a rewrite of existing documentation (2026-11-12): "Distill the
essence and the important points, trash the rest."

Select the content before writing. Decide who reads the text, and keep the facts that
this reader needs in order to understand and to use the item. Leave the other facts out
entirely. Then explain each fact that you keep as fully as the clarity rules require. A
text becomes shorter because facts are left out, never because the explanation of a kept
fact is compressed.

Leave out:

- a description of an internal mechanism that the reader cannot observe and does not need
  in order to use the item;
- a fact that the signature or the types already state;
- a repetition of what the documentation of another item states (link that item
  instead);
- a list of every case where a general statement and one example are enough;
- a remark that would matter only to someone who changes the implementation, in the
  documentation of a public item;
- a qualification that tells the reader nothing, such as ", written as plain text" after
  the description of a syntax.

Keep in every case:

- what the item is and what it is used for;
- the contract of the item: what the caller must provide, what is returned, which errors
  are reported under which conditions, when the item panics, and the defaults;
- every fact whose omission would lead a reader to use the item incorrectly;
- the reason for a design that a user is likely to wonder about;
- pointers to the related items that the reader should know about.

## Wording and sentence structure

The rules of this section add to the documentation clarity rules above. They describe the
wording of user-facing documentation. The wanted style is the style of conventional
technical documentation: the text that an experienced developer writes for other
developers. Part 4 contains samples of this style; read them before writing.

Apply the following test to every sentence. Would an experienced developer say this
sentence to a colleague while explaining the code? If not, rewrite the sentence.

- **Use the established technical term.** The rule against jargon forbids terms that were
  invented for this project. It does not forbid the established vocabulary of
  programming, of LaTeX, or of techy's public API. Do not replace an established term
  with a description in everyday words. BAD: "the spellings to use instead"; "a formula"
  and "running text"; "the file beside the document". Better: "the syntax to use
  instead"; "math mode" and "text mode"; "a sibling file of the document".

- **Describe code with the conventional verbs of technical documentation.** A function
  "returns", "parses", "stores", "calls", "reports an error". A value "contains"
  or "is". Do not describe a program component as a person who "asks",
  "answers", "claims", "knows", "names", "says" or "serves". Do not use "holds",
  "states", "carries" or "keeps" where a more precise verb exists. BAD:
  ```
  /// The citation provider that claimed the citation key could not answer;
  /// the error holds its words.
  ```
  Better:
  ```
  /// The [`CitationProviderError`] structure contains the details (including
  /// the error message) that a citation provider reports when it fails to
  /// retrieve a particular citation key.
  ```

- **Begin a documentation block with a full sentence about the documented item.**
  Do not begin with a noun phrase that is followed by a colon or a dash. For a
  module, write "This module defines …" or "This module provides …". For a type,
  write "A `T` is …" or "This struct stores …". For a function, begin with a
  verb in the third person, which is the Rust convention: "Returns …", "Parses
  …". For a diagnostic condition, state the error directly and give the
  identifier in parentheses, where it does not stand in the way: "Error
  representing a malformed command name (id `<ID>`)." BAD:
  ```
  //! The parse driver, [`FlmDriver`]: the object that holds the behavior and the
  //! settings of a running parse, and the two conditions it reports.
  ```
  Better:
  ```
  //! This module defines [`FlmDriver`], the parse driver of the FLM language,
  //! along with the error conditions that the driver reports.
  ```

- **Write one fact per sentence.** A sentence that joins several facts with colons,
  semicolons and relative clauses is hard to read. Write several sentences, or a list when
  the facts are parallel cases. BAD:
  ```
  /// What a citation provider returns for one citation key: `Ok(Some(answer))`
  /// for a citation key it serves, `Ok(None)` ("not mine") for a citation key it
  /// does not serve, so that the next citation provider is asked, or an error for
  /// a citation key it claims and could not answer.
  ```
  Better:
  ```
  /// The result that a citation provider returns for one citation key.
  ///
  /// - `Ok(Some(answer))`: The provider handles this citation key, and `answer`
  ///   contains the citation entry.
  /// - `Ok(None)`: The provider does not handle this citation key. The key is
  ///   then passed to the next citation provider.
  /// - `Err(error)`: The provider handles this citation key but failed to
  ///   retrieve the entry. The key is not passed to any other provider.
  ```

- **Connect sentences with ordinary linking words.** "For instance", "That is",
  "However", "Therefore", "In this case", "Then", "Also". Make sure the relation
  between different parts of a sentence is obvious to the reader.

- **Say things directly.** Do not describe a thing through a list of indirect questions
  ("how …", "which …", "what …"). BAD: "The driver is a value that holds what
  matters only while a parse runs: how far the parse recovers from a problem,
  how a command name is resolved, which node a paragraph break becomes, …".
  Better: "The driver provides the settings and the callbacks that the parser
  uses during a parse: the error recovery policy, the resolution of command
  names, the type of node created for a paragraph break, …".

- **Repeating a noun is not a fault in technical
  documentation.** Do not vary the term for elegance. Do not replace the term
  with "it", "this" or "the latter" when another noun stands between the term
  and the pronoun. Specific concepts that are well captured by a particular term
  should be defined clearly, so that the term can be used to repeatedly refer to
  that concept. Repeat a technical term if it is defined clearly and the
  definition is obvious to the reader to find/look up. Repeat a definition for a
  term (or link to the API item where it is defined) if the reader might not be
  able to easily find its definition or understand what it means from context.
  Introduce a term in emphasis, for example with a short explanation in the same
  sentence and a concrete instance ("e.g., …"). After that, use exactly this
  term whenever needed.

- **Follow a general statement with a concrete example.** Use literal LaTeX-like source
  or code, introduced by "For instance" or "e.g.". A reader understands "you can
  force document authors to type inline math as `\(...\)` and not as `$...$`"
  faster than a general description of forbidden characters.

- **Give examples of correct usage, not of mistakes.** Negative examples are
  useless: do not show source that is not allowed, and do not list the things
  that are not allowed. State the requirement, and give an example of source
  that meets it ("as in `\R\cite{bib:myref}`"). This holds without exception,
  also for a short instance of the mistake.

- **Describe behavior as the caller observes it.** State what the caller provides,
  what the item returns, which error is reported under which condition, what the
  default is, and what a later call does. Describe the internal mechanism only
  where the caller needs it to use the item correctly.

- **State what an item is before what it is not.** Mention what an item does not
  do only where most readers would otherwise assume it. Do not define an item
  with "X rather than Y", "not X but Y" or "no second X". BAD: "An element is
  […] identified by the element value itself (its allocation) and not by its
  name." Better: "Two element handles refer to the same element if they point to
  the same allocation. The type name does not identify an element; several
  elements can share one type name."

- **You may address the reader as "you" when giving advice**, and state the
  situation in which an item is useful: "Use `X` if you need …", "You can set
  …".

- **Do not write telegraphic text.** No fragments such as "source in, one tree
  out", and no arrows in place of a verb. Write the sentence:
  "[`parse_fragment`] parses FLM source text into a [`Fragment`]."

- **When rewriting existing text, write new text from the facts.** First
  establish from the code what is true about the item. Then write the
  documentation as if none existed. Do not edit the old sentences word by word:
  replacing words keeps the structure of the old sentence, and that structure is
  usually the problem.

## Output strings and diagnostic messages

Output strings and diagnostic messages must obey the same documentation clarity rules as
all user-facing documentation. Diagnostic messages and error messages, in particular,
follow the rules of Part 3.

# Part 3. The rules on diagnostic messages

These are Philippe's rules (I)–(IV) of 2026-09-27, refined from Philippe's own rewording
of FLM's messages in 2026-11. They apply to every message a person can read:
diagnostics, errors, and the detail texts that messages embed. The examples are FLM
messages.

- (I) **Say what is wrong, directly.** Begin with what is wrong and with the
  item it concerns: "Invalid label ‘x’", "Missing value for key ‘k’ of
  ‘enumerate’", "Duplicate definition of label ‘sec:a’", "No entry found for
  citation key ‘k’", "Unsupported element ‘e’ for backend ‘b’", "Failed to
  retrieve bibliography entry for ‘k’: …". When that phrase does not show the
  rule that was broken, state the rule after it: "Invalid label ‘x’: labels must
  have the form ‘type:label’". A rule may also be the whole message: "‘\R’ must
  be followed immediately by ‘\cite’", "Paragraph breaks may not be placed
  inside inline content". "Must" states a requirement, "may not" a prohibition.
  When the error is about something that does not exist but was expected to be
  there, that thing is missing and is clearly stated as such: "Missing proof for
  theorem ‘thm:main’", not "No proof refers to the theorem ‘thm:main’", which
  is "a plain fact rather than a clear statement of what is wrong".
- (II) **Do not mention the recovery**, and do not explain how the program works
  or why it needs what it asks for ("because the parsing settings do not make it
  a delimiter", "the program processing this document reads no files").
- (III) **Give possible fixes only if they are not obvious from the violated
  condition; if one nontrivial fix is listed, list the other important ones
  too.** Write a fix as the text to type, after a semicolon or a colon: "; use
  ‘\%’ for a percent sign, or ‘%%’ to start a comment", ": use the syntax
  ‘key=…’".
- (IV) **Avoid library-specific jargon, especially where an author is the likely
  problem's cause.** Name what the author wrote (the command, environment, key,
  label, file) in the author's words: argument, key, label, template,
  definition, inline content, paragraph break. A message that only a faulty
  program or extension can cause may use the terms of the programming interface
  it concerns (in FLM: backend, lowering rule, block-structure hook, stage; in
  techy: spec, construct parser, hook, parse driver, scope): its reader is the
  program's author. Such a message begins "Misconfigured X ‘name’: …" when a
  configuration or a hook did something wrong, and "X failed: …" or "Failed to
  X: …" when it wraps a failure reported by someone else. The rule is: jargon
  should only be used when an alternative phrasing that would avoid it risks
  confusion, especially confusion as to what is wrong/incorrect.
- (V) **Name the specifics.** Every name and every piece of source text the
  message refers to is the one the person wrote or chose, quoted as written:
  commands with their backslash (‘\input’), placeholders with their ‘#’ (‘#2’).
  Give actual values, not a description of them: "‘\foo’ has arguments
  ‘#1’..‘#3’", not "the definition has 3 numbered argument(s)"; "Workflow ‘X’
  may not be used with option ‘Y’ of feature ‘Z’", not "your workflow needs an
  option of some feature". A fact the message needs is a field of the condition.
- (VI) **No dependent clauses.** No "which…", "whose…", "since…", "because…".
  Join two facts with a colon or a semicolon, and put a secondary fact (a limit,
  the backend concerned, the accepted forms) in parentheses: "Invalid
  placeholder ‘#body’; ‘\foo’ has no body", "Recursion limit reached (64 levels)
  while expanding ‘\foo’", "Invalid short label form ‘ii’ of ‘enumerate’ (short
  form labels must contain exactly one instance of a, A, i, I, or 1)".
- (VII) **Form.** One line; a capital letter first; no final period; every
  quoted name or text between ‘…’, never backticks.
- (VIII) **Prefer one consolidated composed message to a message pieced together
  from multiple templates.** Some diagnostics are composed in a
  nested/hierarchical fashion (hypothetical example: "Error in definition of Z
  -> Problem with argument placeholder #6 -> definition only accepts #1..#5"; or
  this situation also appears if a diagnostic field is an enum that specifies a
  way in which something is wrong). For such diagnostics, it is important to
  compose the message once with all parts in one consolidated template. A message
  like `Invalid argument reference ‘#6’ in definition of ‘\Z’, expected
  ‘#1’...‘#5’` is way more readable than "Argument expansion failed in
  definition of Z: Problem with argument #6: This definition has only 5 numbered
  arguments".

## 1. API documentation

### 1.1 A type: what it is, then one aspect per paragraph

From the documentation of `LatexTokenReaderBase`:

> Base class for token readers.
>
> A token reader is able to transform input characters (usually given as a single string)
> into *tokens*. Tokens are instances of `LatexToken`.
>
> A token reader also has an internal position pointer that remembers where in the string
> we should continue to read more tokens. A call to `next_token()` will both parse a new
> token and advance the internal position pointer past the token that was just read, such
> that future calls to `next_token()` continue parsing tokens as they appear in the
> string.
>
> A token reader should at minimum provide implementations to `peek_token()`,
> `move_to_token()`, `move_past_token()`, and `cur_pos()`.
>
> A token reader can (but does not have to) also provide character-level access to the
> input. This can be used by some special parsers like verbatim parsers. In this case,
> the token reader should implement `peek_chars()`, `next_chars()`, and
> `move_to_pos_chars()`.

Points to notice:

- The first sentence states what the type is.
- The second paragraph defines the central term ("token reader") in one sentence, in
  established terms, and marks the new term "tokens" with emphasis.
- Each following paragraph covers one aspect, and each begins with the same subject, "A
  token reader".
- The text tells an implementer which methods to provide.

### 1.2 A type with a design reason

From the documentation of `ParsingState`:

> Stores some information about the current parsing state, such as whether we are
> currently in a math mode block.
>
> One of the ideas of `pylatexenc` is to make the parsing of LaTeX code mostly
> state-independent mark-up parsing (in contrast to a full TeX engine, whose state
> constantly changes and whose parsing behavior is altered dynamically while parsing).
> However a minimal state of the context might come in handy sometimes. Perhaps some
> macros or specials should behave differently in math mode than in text mode.
>
> This class also stores some essential information that is associated with `LatexNode`'s
> and which provides a context to better understand the node structure. For instance, we
> store the original parsed string, and each node refers to which part of the string they
> represent.

Points to notice:

- The first sentence states what the type stores and gives one concrete instance ("such
  as whether we are currently in a math mode block").
- The design reason has its own paragraph. It is told as an ordinary explanation, with
  "However" and "Perhaps", and it ends with a concrete case.
- "For instance" introduces a concrete example of the general statement before it.

### 1.3 Methods: the effect that the caller observes

> **`move_to_token(tok, rewind_pre_space=True)`**
>
> Move the internal position pointer of this token reader to point to the position of the
> given token `tok`. That is, a subsequent call to `peek_token()` or `next_token()`
> should read the given token again.
>
> For token readers that can worry about whitespace, if `rewind_pre_space=True`, then the
> internal position is set to point on the whitespace that precedes the token `tok` (as
> specified in the instance `tok`); if `rewind_pre_space=False` the internal position
> pointer is set to point on the actual token after the preceding whitespace.

> **`peek_token(parsing_state)`**
>
> Parse a single token at the current position in the input stream. Parsing is
> influenced by the given `parsing_state`. (See `ParsingState`.)
>
> The internal position pointer is not updated. I.e., a subsequent call to `peek_token()`
> with the same parsing state should return the same token.
>
> If the end of stream is reached, i.e., if there are no remaining tokens at the current
> internal position, then `LatexWalkerEndOfStream` is raised.

> **`peek_token_or_none(parsing_state)`**
>
> A convenience method that calls `peek_token()`, but that returns `None` instead of
> raising `LatexWalkerEndOfStream`.

> **`next_token(parsing_state)`**
>
> Same as `peek_token()`, but then also updates the internal position pointer of this
> token reader to advance past the token that was read.

Points to notice:

- The first sentence states the action. "That is" or "I.e." then restates the action as
  the effect that the caller observes on the next call.
- Each parameter is explained by its effect for each value ("if `rewind_pre_space=True`,
  then …; if `rewind_pre_space=False` …").
- The error condition is one sentence of the form "If …, then … is raised".
- A method that is a variant of another method is documented by its difference from that
  method ("Same as `peek_token()`, but then also …").

### 1.4 Fields and options: purpose, a use case, the accepted values, the default

> **`forbidden_characters`**
>
> Characters that are simply forbidden to occur as regular characters. You can use this
> for instance if you'd like to disable some LaTeX-like features but cause the
> corresponding character to raise an error. For instance, you can force inline math to
> be typed as `\(...\)` and not as `$...$`, and yet still force users to type `\$` for a
> dollar sign by including '$' in the list of forbidden characters.
>
> The `forbidden_characters` can be a string, or a list of single-character strings; this
> attribute will be used with the syntax `if (c in forbidden_characters): ...`

> **`math_mode_delimiter`**
>
> Information about the kind of math mode we are currently in, if `in_math_mode` is
> `True`. This is a string which can be set to aid the parser. The parser sets this
> field to the math mode delimiter that initiated the math mode (one of `'$'`, `'$$'`,
> `r'\('`, `r'\['`). For user-initiated math modes (e.g. by a custom environment
> definition), you can set this string to any custom value EXCEPT any of the core math
> mode delimiters listed above.

> **`keep_comments=True|False`**
>
> If set to `True`, then LaTeX comments are kept (including the percent-sign); otherwise
> they are discarded. (By default this is `False`)

Points to notice:

- The text addresses the reader as "you" when it gives advice, and it names a situation
  in which the reader would use the field ("You can use this for instance if you'd like
  to …").
- The example uses literal source text (`\(...\)`, `$...$`, `\$`).
- The accepted values and the default are stated.

From FLM's documentation rules, Philippe's rewrite of the description of the feature

### 4.3 The documentation of two diagnostic conditions (2026-11-12)

Both texts before were written by the `documenter` agent in a trial run. Philippe judged
them "not good" and "disastrous", and rewrote them.

The condition `flm.citations.no-key`:

- Before: "Error: a `\cite` call has no citation key (id `flm.citations.no-key`). For
  example, `\cite{}` or `\cite{ , }`. Reported by the lowering rule of `\cite`, at the
  call. The call shows nothing; a citation chunk with nothing left to show is shown as a
  dropped mark (`flm.pres.dropped`)."
- After: "The error that is reported when a `\cite` call has an empty argument (id
  `flm.citations.no-key`). Reported by the lowering rule of `\cite` when it is invoked.
  The call site itself expands to a dropped mark (`flm.pres.dropped`)."
- Philippe's first version of this text contained "for instance `\cite{}` or
  `\cite{ , }`" after "empty argument". Philippe removed these instances of the mistake
  afterwards: "remove `\cite{}` and `\cite{ , }` from the 'good example', it's
  misleading."
- Philippe's comment: "How can a call 'show' anything? that just would not make any
  sense. What is a 'citation chunk'?? And I'm assuming the statement of the general rule
  'a citation chunk with nothing left to show is shown as a dropped mark' is meant as an
  implication that \cite{} has nothing left to show?? way too convoluted and unclear."

The condition `flm.citations.no-citation`:

- Before: "Error: an `\R` has no `\cite` directly after it (id
  `flm.citations.no-citation`). For example, `\R text` or `\R{\cite{a}}`. Reported by the
  lowering rule of `\R`, at the `\R`. The `\R` is shown as a dropped mark
  (`flm.pres.dropped`); a `\cite` written further on is a citation chunk of its own."
- After: "Error raised when a `\R` is not immediately followed by `\cite`
  (`flm.citations.no-citation`). The `\R` command must immediately be followed by a
  valid `\cite{..}` command invocation, as in `\R\cite{bib:myref}` or
  `\R[I]\cite{bib:myref,bib:myref2}`. Reported by the lowering rule for `\R` when `\R` is
  invoked. In such a case, the `\R` expands to a dropped mark (`flm.pres.dropped`)."

Points to notice (an interpretation):

- The first sentence is a full sentence about the error: "The error that is reported
  when …" or "Error raised when …". It does not use "Error:" followed by a clause.
- The condition is stated as the author sees it ("has an empty argument", "is not
  immediately followed by `\cite`").
- A requirement on the syntax is stated positively, with examples of correct source
  (`\R\cite{bib:myref}`). The text gives no example of the mistake.
- A command "expands to" something. It does not "show" anything, and nothing "is shown
  as" something.
- The text uses no term that it does not define. "Citation chunk" is a term of the
  implementation, and the reader does not know it.
- The consequence is stated for this case directly ("The call site itself expands to a
  dropped mark"). The text does not state a general rule and leave the reader to apply
  it to the case.
- The place of the report is stated with a clause ("when it is invoked"), not with a
  fragment ("at the call").
- Detail that the reader does not need is left out ("a `\cite` written further on is a
  citation chunk of its own").

### 4.4 Philippe's judgment of three rewrites of the xnotes conditions (2026-11-12)

Three models rewrote the documentation of the diagnostic conditions of FLM's xnotes
feature. Philippe read the three results without knowing which model wrote which, and
judged one result good and the two others "okayish/meh". The texts of this section come
from that judgment.

**Texts that Philippe approved.** Philippe named their qualities: "better phrasing
choices; better balance", "better step-by-step disentanglement of explanations".

The condition `flm.xnotes.empty`. Philippe: the text "gets correctly" that the sentence
on what counts as empty "is best explained as a separate sentence".

> The warning that is reported when an xnote has no content (id `flm.xnotes.empty`).
> Content that consists only of whitespace (including `~` and `\ `) and comments counts
> as empty.
>
> Reported by the lowering rule of the xnote when it is invoked. The xnote is otherwise
> processed as usual, with empty content: its mark is written, and for an xnote kind with
> a list, the entry of the xnote in the list is empty.

The condition `flm.xnotes.entry-outside-list`. Philippe: "much better structure and
phrasing for the explanation".

> Error representing an entry of a list of xnotes ([`ENTRY`](super::ENTRY)) that is
> lowered by its own lowering rule (id `flm.xnotes.entry-outside-list`).
>
> The lowering rule of a list of xnotes lowers the content of each entry itself, and
> never invokes the lowering rule of the entry. An entry is therefore lowered by its own
> rule only when a stage placed it outside a list, or when the lowering rule of its list
> lowers the children of the list one by one.
>
> A document cannot cause this error: it is caused by a faulty stage or lowering rule.
> Reported by [`EntryRule`](super::EntryRule). The entry expands to nothing.

The condition `flm.xnotes.unpaired`. Philippe: "very good unpacking of the explanation".

> Error representing an element that declares a different number of xnotes of one kind in
> its reference points and in its [`XnoteSource`](super::XnoteSource) aspect (id
> `flm.xnotes.unpaired`).
>
> An element that carries xnotes declares each xnote twice. First, it declares one
> reference point for each xnote, with [`ref_points`](super::ref_points). Second, its
> [`XnoteSource`](super::XnoteSource) aspect returns the region of the node that contains
> the content of each xnote. For each xnote kind, both must declare the same number of
> xnotes.
>
> A document cannot cause this error: it is caused by the feature that defines the
> element. Reported by the collect stage [`COLLECT`](super::COLLECT) once for each such
> node and xnote kind. The xnotes of the node are paired with the content regions in
> order. An xnote without a content region has empty content. A content region without
> an xnote is not written, and the lowering rule of the element reports
