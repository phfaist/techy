# Code Review Reports

AI agents were instructed to review various source files of this project.  The reports are collected here.

## Source file `src/constructs/arguments_parser.rs`

(Relevant parts extracted manually from Opus' prompt output.)

1. Duplicated comment-node reconstruction (maintainability).
Lines 124–127 are byte-for-byte identical (same code and same explanatory comment) to nodes_parser.rs:593–596:
let content_span = Span::new(post_space.start - content.len(), post_space.start);
let start_span = Span::new(token.span.start, content_span.start);
let kind = NodeKind::comment(start_span, content_span, *post_space);
Two independent sites reconstruct the three sub-spans of a Comment token. A shared constructor — e.g. NodeKind::comment_from_token(&token) or a helper on TokenKind::Comment — would DRY this and keep the "span = delimiter + content + post-space" invariant in one place. Low priority, but this is exactly the kind of parallel logic that drifts.

2. Eager display allocation in the expression command path (efficiency).
parse_expression_node, line 220:
let display = format!("{}{}", escape_char, name);
This String is built for every command-in-expression dispatch (\frac1\alpha, etc.) but is consumed only on the rare requires-arguments error branch inside dispatch_expression_invocation (lines 271–274). The Specials arm already passes a borrowed name with no allocation (line 251). Consider deferring the format into the error branch (or passing the pieces) so the common zero-arg dispatch doesn't allocate. Micro-optimization — flagging because it's a per-invocation cost on the hot path, and the fix is local.

3. GroupArgumentParser fallback consumes a group of any class (design note, not a bug).
When the delimited-form class check fails (line 415), control falls to parse_expression_node, whose GroupOpen arm accepts a group of any class in scope (lines 205–213). So \frac[x]{y} — with […] registered as a group class — would swallow the whole [x] bracket group as \frac's first argument rather than treating [ as a single char. This matches the documented "expression = a delimited group of any class in scope" semantics and isn't exercised by the test rules (only brace is registered), so it may be fully intended. Worth a one-line doc note on GroupArgumentParser if the intent is specifically "my class as a group, everything else as a single token," since a reader could reasonably expect the fallback to be char-only.

Regarding Test coverage. One small gap I'd suggest: there's no test for a mandatory group argument whose delta affects tokenization interacting with the noise scan — e.g. a comment appearing in the noise while comments are disabled by the argument's delta. per_argument_state_delta_scopes_the_arguments_extent covers the delta scoping inside the group, but not a noise-scan token classified under the argument delta. Likely fine given scan_argument_noise runs under cx.state (the argument state), but it's an untested corner.

## Source file `src/constructs/nodes_parser.rs`

(Phase 6.2 — content dispatch loop core. Reviewed by an Opus agent; no correctness bugs found. Findings lean toward maintainability, robustness, and test gaps.)

**1. Comment sub-span reconstruction is duplicated and fragile (maintainability / robustness) — `nodes_parser.rs:593-596`, duplicated at `argument_parsers.rs:120-127`**
The three comment sub-spans are reconstructed by byte arithmetic:
```rust
let content_span = Span::new(post_space.start - content.len(), post_space.start);
let start_span = Span::new(token.span.start, content_span.start);
```
This exact block (comment included) is copy-pasted in `argument_parsers.rs:124-127` — the existing report already flagged this, and it's confirmed identical. Two concerns:
- The reconstruction only works because `TokenKind::Comment.content` is currently a raw source slice (`&'s str`), so `content.len()` equals its byte span (`token/token.rs:92-94`). It carries the content *string* but not a content *span*. Any future normalization/decoding of comment content (or a reader that synthesizes content) silently breaks both the span math and the partition invariant.
- `post_space.start - content.len()` is unchecked `usize` subtraction (line 594). It cannot underflow with today's invariants (content sits after a ≥1-byte start delimiter), but CLAUDE.md forbids panic paths in lib code, and this one is one broken invariant away from a debug panic / release wraparound.

Suggested fix: have `TokenKind::Comment` carry the content span (or start-delimiter span) directly, or add one shared helper (e.g. `fn comment_subspans(token) -> (Span, Span, Span)`) used by both call sites. Either removes the duplication and the fragile subtraction at once.

**2. `GroupClose` stop matching is correct — the `]`-closes-`{` class-vs-delim bug is handled (design-note / not a bug) — `nodes_parser.rs:393-398`, `716-728`**
The docs warn about a close matching on class alone. The code correctly requires *both* `delim == close` **and** `group_close_type(state, delim) == Some(*group_type)`, re-resolving the class against the same `cx.state` the tokenizer used. The four adversarial cases (shared class + different delim, reclassifying delta, expected-close path, delimiter-table path) are each covered by a dedicated test (`nodes_parser.rs:1337-1408`). Calling this out explicitly so it is not re-flagged: working as designed.

**3. `.expect("the node was just staged")` is a library-code panic path (robustness, low) — `nodes_parser.rs:375`**
`test_node_stop` does `staged.get(id).expect(...)`. It is a genuine internal invariant (the id was just returned by `stage`), so it cannot realistically fire, but it is the one non-debug `expect` on the hot path and technically violates the "never panic in lib code" rule. Acceptable as-is; if you want strictness, treating a missing id as "condition did not fire" (`false`) would degrade gracefully instead of aborting. Low priority.

**4. Loop-progress depends on an unstated `resume_pos` advancement contract (robustness) — `nodes_parser.rs:496-510`, `530-707`**
Every non-terminal arm makes progress by consuming a token (`move_past`). Recovery placeholders (`recovered == true`) are deliberately *not* consumed here; progress then relies entirely on `resume_at(cx.tokens, recovery.resume_pos)` having moved the reader strictly past the tokenizer error. If a `TokenRecovery` ever yields a `resume_pos` at or before the error position, the next `peek` re-hits the same error and the loop spins forever. This is a token-layer contract, not a bug in this file, but it is load-bearing and unasserted here. Consider a `debug_assert!` that the reader position advanced after `resume_at`, or documenting the contract at the peek site (line 505).

**5. Deferred diagnostic when a node condition pre-empts an unresolvable command (design-note / test-coverage) — `nodes_parser.rs:423-428`**
In `recover_as_chars`, if `flush_through` reports the node condition fired on the preceding run, the function returns `Ok(true)` *before* `cx.recover(...)`, so the "cannot resolve command" diagnostic is not emitted and the command token is left unconsumed for re-processing. This is consistent (the diagnostic is emitted when the caller re-encounters the command), but it means diagnostic count depends on whether a node condition is active — a subtle behavior with no test. Worth a one-line test asserting the diagnostic is deferred (not lost), or a doc note on the intended ordering.

**6. Minor test-coverage gaps for consume/predicate/callable-node paths (test-coverage) — tests region `nodes_parser.rs:1259-1602`, `1717-2119`**
Coverage is broad, but a few decided behaviors lack a direct test:
- `consume = true` is exercised only for `Command` (line 1453) and `GroupClose` (1479); not for `ParagraphBreak` or `Predicate` stop kinds (the post-space handling differs — a `ParagraphBreak`/predicate-matched comment carries post-space that `move_past(..., true)` would swallow).
- The node stop condition firing on a `Callable` (invocation) node — groups are covered (`node_condition_counts_a_group_as_one_node`, 2208) but dispatched invocations are not, despite `dispatch_invocation` ending in `test_node_stop` (line 474).
None are correctness concerns; they're the untested corners of otherwise-tested machinery.

**7. State is correctly restored on the error path (invariant, confirmed OK) — `nodes_parser.rs:462-466`, `698-701`**
Both descent sites do `cx.state = outer_state;` *before* the `?` on the child parser's result, so an aborting sub-parse never leaks the swapped child state to the caller. The invocation after-effect delta is applied to the loop's own state (line 472) and later discarded by the caller's own structural revert. Verified correct; flagged so it isn't mistaken for a leak.

**Summary:** No correctness bugs found. Prioritize **#1** (unify + harden the comment sub-span reconstruction — duplicated across two files and the only fragile arithmetic in the module). **#4** and **#5** are cheap robustness/clarity hardening. The rest are low-priority notes.

## Source file `src/constructs/group_parser.rs`

(Phase 6.3 — groups. Reviewed by an Opus agent; no correctness bugs found. `cargo test group_parser` passes 2/2.)

**Summary:** A clean, correct implementation. Both priority-1 concerns check out: the GroupClose stop condition passes **both** `group_type` and `close` (`group_parser.rs:104-107`) and `NodesParser::token_stop` matches them conjunctively (`delim == close && group_close_type(...) == Some(*group_type)`, `nodes_parser.rs:393-397`), excluding the `]`-closes-`{` and reclassified-`}` bugs. Structural state is reverted before any `?`, so no state leaks on abort. Span arithmetic partitions correctly in all three exit paths.

**1. State revert is correctly abort-safe — verified, not a bug (correctness) — `group_parser.rs:111-114`.** `cx.state` is restored (`cx.state = outer_state`) *before* `result?` unwinds, so a strict-mode abort inside the interior parse leaves `cx.state` at the caller's value. Same pattern in the two `cx.recover(...)?` recovery branches. Flagged as a positive because it's the easiest thing to get wrong here.

**2. `unreachable!` on `StopCause::NodeCondition` panics in release (robustness / design-note) — `group_parser.rs:144-146`.** The branch is genuinely unreachable — `GroupParser` builds its `StopSpec` via `StopSpec::at_token(...)`, which sets `node: None` (`nodes_parser.rs:175-177`), so `NodesParser` can never return `NodeCondition`. This mirrors an existing `unreachable!` in `nodes_parser.rs:282`, so it's consistent with codebase convention and defensible as an invariant assertion; still worth a conscious call on whether these should be `debug_assert!`-guarded or folded into the `EndOfInput` handling. Low priority.

**3. EOF end position relies on reader `pos()` semantics — verified correct (correctness) — `group_parser.rs:131`.** Uses `cx.tokens.pos()` as the group's `end` in the unclosed-at-EOF path. After the interior parse hits `EndOfStream`, `NodesParser` flushes the terminal token's pre-space (trailing whitespace) into the interior siblings and does `move_to(&token, false)`, leaving `pos() == EndOfStream.span.start`, which equals the end of the last flushed interior node. So the partition invariant holds for `"{"`, `"{ab"`, and `"{ab  "` alike, and `StdTokenReader`/`TokenListReader` agree. Correct — noted because it's non-obvious and depends on the NodesParser flush contract.

**4. `UnexpectedGroupClose` diagnostic wording (maintainability) — `group_parser.rs:138`.** Emits `"unclosed group: expected '{close}'"` for what is actually a *mismatched / stray* close (a `]` under a `{`, or a re-classed `}`), pointing at the stray token's span. Consider distinct wording (e.g. `"mismatched group close: expected '{close}'"`) to help users distinguish the two recovery situations from the EOF message. Cosmetic.

**5. Own-file test coverage is thin; substantive paths covered by integration tests elsewhere (test-coverage) — `group_parser.rs:253-282`.** Only two direct-drive tests (well-formed round-trip under `Strict`; unclosed-at-EOF under `Tolerant`). Not exercised via the direct-drive harness: the `UnexpectedGroupClose` unwind, strict-mode abort (EOF and mismatch), `with_child_states`, nested groups, ambiguous-`$` interior-state derivation. These *are* all covered by `nodes_parser.rs` integration tests (e.g. `unclosed_group_strict_aborts`, `mismatched_close_inside_a_group_unwinds_without_consuming`, `ambiguous_dollar_group_closes_via_the_derived_expected_close`, `sibling_group_interiors_share_one_memoized_state`). Coverage is adequate overall; optional to make the file self-covering.

**6. `self.child_states.clone()` on each parse (efficiency) — `group_parser.rs:110`.** The clone is shallow (Arcs + borrowed `&dyn Fn`), so cost is negligible. `core::mem::take(&mut self.child_states)` would avoid it entirely, but `&mut self` permits re-invocation in principle, so the defensive clone is reasonable. Trivial; leave as-is.

**7. Doc-reference precision (maintainability / doc-note) — `group_parser.rs:25`.** The module header cites "(DESIGN_RATIONALE.md §3.6, §3.8)" for matching-and-recovery, but the rule that an unclosed group records an **empty `close` TextContent** is documented in §3.5 (alongside the `GroupData` definition). Adding §3.5 to the header cross-reference would be accurate. Cosmetic.

**Checked and found correct:** GroupData construction (`group_type: Some`, span-backed `open`/`close`, `ext: Default`); the recorded close is the exact delimiter span (GroupClose tokens carry no post-space); interior-state derivation goes through the session memo (`group_interior_state`) which always sets `expecting_group_close = rule`, guaranteeing the close stays recognizable (the `$…$` case); the outer (restored) state is attached to the group node while children were staged under the interior state; naming conforms to NAMING_STRATEGY.

## Source file `src/constructs/invocation_parser.rs`

(Phase 6.4/6.5 — invocation dispatch. Reviewed by an Opus agent; no correctness bugs found. All 24 argument tests pass.)

**Overall:** A clean, well-documented file that correctly implements the Phase 6.4/6.5 contract. The critical invariants — whole-trigger consumption, non-over-claimed post-space, per-argument state scoping with pre-`?` revert, and coordinate consistency between the flat child list and region-relative content offsets — all hold. Findings are minor plus one genuine test-coverage gap.

**1. Post-space handling is correct — no over-claiming, no double-count (correctness, verified) — `invocation_parser.rs:164`.** `post_space: TextContent::Spanned(token.post_space())` records exactly the trigger token's own syntactic post-space (`Command`/`Comment` kinds only; empty span at `span.end` otherwise, `token.rs:149-156`), matching the July 2026 amendment. The dispatch arm consumes the trigger whole first (`nodes_parser.rs:459`, `move_past(invocation.token, true)`), so `cx.tokens.pos() == token.span.end` on entry and `scan_argument_noise` cannot re-scan the post-space bytes. For `\frac 1 2` the recorded post-space sits between name and first region (span `5..6`); for `\& b` it is empty and the following space falls through to the caller as sibling content. Flagged as highest-priority because it is the file's riskiest invariant and it holds.

**2. Span-end relies on "last staged child is the source-rightmost node" (maintainability) — `invocation_parser.rs:149-155`.** `end` is taken from `children.last()`'s span end — correct for every standard argument shape, but an unstated invariant rather than a computed maximum. Since `parse_declared_arguments` is shared with the Phase 6.6 environment-shaped compositions (`invocation_parser.rs:85`), a future custom `ArgumentParser` whose region ends on a non-rightmost node would silently produce a too-short node span. Suggest a one-line comment pinning the assumption at line 149 (computing a `max()` is a per-invocation cost you likely don't want).

**3. Zero-arg / single-char-command post-space cases untested directly (test-coverage) — recommended action.** The 24 tests exercise `StdInvocationParser` end-to-end well, but two gaps: (a) no direct test of a callable with **zero declared arguments** asserting the trigger-only span and `post_space` (`\alpha` is dispatched in `expression_fallback_dispatches_a_full_invocation` but its span/post_space are never asserted); (b) the module's headline amendment example — a **single-character command** like `\& b` where post-space is empty and the trailing space must become sibling content — is not tested anywhere. Suggest adding: a zero-arg macro `\x` in `\x y` asserting `span == 0..2`, `post_space == ""`, sibling `" y"`; plus a multi-char `\x y` variant asserting `post_space == " "` and span including it. This is the exact behavior the July 2026 amendment turns on, only tested indirectly.

**4. Per-argument state restore is not unwind-safe (robustness, low) — `invocation_parser.rs:96-98`.** `cx.state` is swapped to `argument_state` and restored by plain assignment after `parse_argument`. If the argument parser panics, `cx.state` is left as the argument state. Acceptable under the project's abort-not-panic policy (an unwind tears down the borrowed `cx`), and `result?` propagates *after* the restore so the ordinary `Err` path leaks nothing. A `scopeguard`/`Drop`-based restore would be over-engineering. No change recommended.

**5. Per-invocation `Vec` allocations lack capacity hints (efficiency, low) — `invocation_parser.rs:89-90`.** `arguments` grows to exactly `argument_specs.len()`; `Vec::with_capacity(argument_specs.len())` avoids reallocation on multi-argument callables. Combined with the per-invocation `Box<dyn ConstructParser>` (decision 2's noted cost) and the required owned name copy (`name.into()`, line 160 — necessary), the hot path does several small allocations; only the `arguments` capacity hint is a free win. Minor.

**6. `.expect` builder read-backs (robustness, design-consistent) — `invocation_parser.rs:152`.** `.expect("the child was just staged")` is a panic in lib code, but it is the established builder-readback idiom (same pattern in `argument_parsers.rs:461`, `builder.rs`) governed by the builder's documented "panic on caller bug" policy. Unreachable in practice. Consistent with design; no change.

**7. Coordinate handling between flat child list and region-relative content is correct (correctness, verified) — `invocation_parser.rs:100-108`.** `children.extend_from_slice(&region.nodes)` builds one flat list across all arguments; `ChildRegion::new(start..end, region.content)` stores region offsets in combined-list coordinates while `region.content`'s `InRegion(..)` stays region-relative. Traced against `builder.rs:306-311`, which resolves `InRegion(r)` off the *resolved* region start — so the two coordinate bases compose correctly (e.g. `\frac 1 2` arg1 resolves content to `"2"`, not the noise space). No off-by-one. Confirmed by `single_token_fallback_stages_whitespace_as_region_noise`.

**Net:** No blocking issues. Recommended action is **#3** (add the zero-arg / single-char-command post-space tests), plus optionally the **#2** comment and **#5** capacity hint.

## Source file `src/token/list_reader.rs`

(Phase 6.1 — `TokenListReader`, a `TokenReader` over a pre-built `Vec<Token>` for isolated construct-parser tests. Reviewed by an Opus agent; a faithful reimplementation, 8/8 tests pass. `move_past`/`move_to`/`pos` are byte-for-byte identical to `StdTokenReader` and compute purely from the passed token's spans, so all fidelity risk concentrates in `peek` + `current()`.)

**1. Synthesized EndOfStream is a second, undocumented divergence from `StdTokenReader` (fidelity / design-note) — `list_reader.rs:89-93`.** The module doc (lines 18-23) claims the *only* inherent difference is the fixed list's inability to re-scan under momentary state. But the `None` branch synthesizes `EndOfStream` as `Span::empty(self.pos)` with **empty pre_space**, which diverges independently of re-scanning. Scenario: build a list from `scan("x  ")` but omit the trailing EOS token → `[Char('x') 0..1]`. After `next()`, `pos = 1`, and `peek()` yields `EndOfStream { span: empty(1), pre_space: empty(1) }`, whereas `StdTokenReader` on the same content yields `EndOfStream { span: empty(3), pre_space: 1..3 }` — both the terminal byte position and the trailing-whitespace pre_space differ. The root cause is inherent (a list without a trailing EOS carries no content-length or trailing-whitespace info), so it is not fixable in code, but the doc overstates equivalence: lines 18-23 and line 41 should be amended to note a synthesized EOS cannot reproduce trailing-whitespace pre_space or a terminal position beyond the last token's `span.end`. In practice `scan()` always appends EOS, so tests don't hit it.

**2. The documented `\verb`/in-span divergence is asserted nowhere (test-coverage) — tests around `list_reader.rs:230-235`.** The headline fidelity limit — `move_past(tok, false)` landing *inside* a token's span, after which `peek` returns the *following* listed token rather than re-scanning the post-space bytes (lines 18-23) — is never pinned by a test. `move_past_and_move_to_flags_match_std_reader` sets `pos = 6` via `move_past(false)` and checks `pos`, but never `peek`s there. A future change to `current()` could silently alter this behavior with all tests green. Suggest a test that, at that in-span position, asserts `TokenListReader` yields the following token AND explicitly asserts it differs from `StdTokenReader` — turning the prose contract into an executable one.

**3. `current()` lookup is correct and efficient — confirms faithful positioning (correctness, positive) — `list_reader.rs:69-72`.** `partition_point(|t| t.span.start < self.pos)` returns the first token with `span.start >= pos`. Because `pre_space.end == span.start` by convention, for any position at or before a token's start the clip `pre_space.start.max(pos).min(pre_space.end)` reproduces `StdTokenReader`'s `skip_whitespace`-derived pre_space exactly (verified against `reader.rs:157-158`). O(log n), not a linear scan. The `.min(pre_space.end)` also defensively prevents an inverted span if a hand-built token violates adjacency. This is the core of the file and it is sound.

**4. `move_past(tok, false)` can panic on subtraction underflow for hand-built tokens (robustness) — `list_reader.rs:101`.** `self.pos = tok.span.end - tok.post_space().len()` underflows (panic) if a hand-constructed token has `post_space().len() > span.end`. `StdTokenReader` has the identical line (`reader.rs:390`), so it's parity, not a regression — but this reader's entire purpose is hand-built lists, where malformed tokens are far more likely. Consider a `debug_assert!(tok.post_space().end <= tok.span.end)` to fail loudly rather than underflow-panic.

**5. `move_to_pos` drops the boundary/bounds guards `StdTokenReader` has (robustness / maintainability) — `list_reader.rs:64-66`.** `StdTokenReader::move_to_pos` (`reader.rs:141-145`) debug-asserts `pos <= content.len()` and char-boundary; this version sets `self.pos = pos` with no checks. There's no content here so those exact checks don't apply, but an out-of-order position silently produces the "following token" behavior with no diagnostic. Low priority given the fidelity limit is documented; a debug-only sanity note would help hand-built-list authors.

**6. `new()`'s invariant check is weaker than what `peek` relies on (maintainability) — `list_reader.rs:50-53`.** The debug_assert verifies only ascending, non-overlapping spans (`w[0].span.end <= w[1].span.start`). But `peek`'s clip fidelity additionally relies on `pre_space.end == span.start` and each token's pre_space lying in the gap after the previous token (`w[1].pre_space.start >= w[0].span.end`). A list satisfying the span-order assert but violating pre_space adjacency would clip incorrectly with no early warning. Consider strengthening the assert to also check these.

**7. `move_past`/`move_to` accept any token without verifying list membership (design-note) — `list_reader.rs:97-111`.** Both compute the new position purely from the passed token's span fields and never confirm the token came from `self.tokens`; a foreign/stale token silently repositions to arbitrary bytes. This mirrors `StdTokenReader` (intentional — the trait contract is position-from-token), so not a bug; for an isolated hand-built-list harness a membership `debug_assert` would be a cheap safety net.

**Coverage present and good:** round-trip parity against a scanned sequence, lockstep movement-matrix parity vs `StdTokenReader`, idempotent/terminal EOS parity for trailing whitespace *with* the EOS token present, mid-whitespace pre_space clipping, empty list, rewind-to-earlier-token. Main gaps are items 1 and 2.

## Source file `src/node/invariants.rs`

(Phase 6.3 — `check_tree_invariants`, a public test utility validating parsed trees, applied retroactively to the whole suite. Reviewed by an Opus agent. For well-formed parser output, all four rule families are genuinely enforced with no constructible false-pass; the `NodeKind` match is compiler-exhaustive. Findings are mostly latent gaps, robustness, and one notable test-coverage hole.)

**1. No negative tests for the callable/region/post-space logic — the most complex and most-amended code has zero broken-tree tests (test-coverage) — `invariants.rs:402-541`.** The three `#[should_panic]` tests cover only Chars-content, List-sibling-gap, and Group-open-delimiter. There is **no** negative test feeding a deliberately-broken *Callable*: region tiling gap/overlap (`check_regions`, 324-399), children-block non-contiguity (248-271), the revised rule-3 post-space position (226-244), content escaping its region subtree (355-391), nor the reachability/multi-parent/unreachable-node asserts (70-85). Since a false pass is the most damaging bug class here, this means a future refactor could silently weaken exactly the hardest-to-reason-about code. There's also no *positive* callable test in this file (all builders use Chars/Group/List); the callable path is validated only indirectly via `environment_parser.rs`/`argument_parsers.rs`/`nodes_parser.rs`/`node/mod.rs` tests. Suggest `#[should_panic]` tests staging a callable with (a) a region-tiling gap, (b) a post-space whose `end` misses the first child, (c) a node in two children ranges, (d) an unreachable node.

**2. Callable post-space is not verified whitespace-only, and its `start` is loosely bounded (completeness / minor) — `invariants.rs:236-244`.** Rule 3 (DESIGN_RATIONALE §3.5) pins post-space as the trigger token's own syntactic post-space, whitespace-only by construction. The checker asserts `s.end == expected_end && s.start >= span.start` but never checks the payload is whitespace, nor that `s.start` is at/after the name. A malformed post-space swallowing non-whitespace name bytes (`s.start == span.start`, covering the whole `\foo`) would pass. Likely intentional (whitespace is `Lang`-defined and not cheaply checkable here), but worth an explicit note. Same unchecked-whitespace observation applies to Comment `post_space` (160-168).

**3. Comment interior byte-accounting is only checked when *all three* parts are `Spanned` (completeness) — `invariants.rs:169-181`.** The partition `start.end == content.start && content.end == post_space.start` runs only inside the all-`Spanned` `if let`. If `content` were `Owned` while `start`/`post_space` are `Spanned`, an internal gap/overlap between delimiter and post-space would go undetected. Not reachable from current parser output (rule 1 makes fresh comments all-`Spanned`; `materialize()` makes them all-`Owned`), so a latent gap for future synthesized/transformed comments, not a live false-pass.

**4. Group interior arithmetic trusts `Owned` delimiter lengths without verifying they physically occupy the span (design-note / latent false-failure) — `invariants.rs:193-221`.** `text_len` computes the interior as `span.start + open_len .. span.end - close_len` but skips the positional prefix/suffix checks for `Owned` delimiters. For a *synthesized* group whose span covers only its interior with `Owned` delimiters corresponding to no physical bytes (constructible via `GroupData::untyped`), the interior would be miscomputed and the partition check would wrongly fail (or wrongly succeed if lengths line up). Out of current scope (`materialize()` preserves lengths byte-for-byte, per the `accepts_a_materialized_tree` test); worth a one-line comment recording the "span physically contains the delimiters" assumption.

**5. The root skipped-byte exemption described in the module doc is not actually coded (design-note) — `invariants.rs:1-5` + `check_interior_partition:279-306`.** A `List`'s interior is its whole span (186) and the partition is required exact (`pos == interior.end`, 298). **1. `group_interior_memo` is an unbounded, linearly-scanned `Vec` — O(n²) time and monotonic retention over a parse (efficiency / robustness) — `mod.rs:53-54, 107-111`.** The memo is a `Vec<(Arc<ParsingState>, Arc<GroupRule>, Arc<ParsingState>)>` scanned with `.iter().find(...)` on every group descent. Two consequences on large/deeply-nested input: (a) *time* — each descent is an O(n) scan over all prior distinct `(base, rule)` pairs, worst-case O(n²) across a parse, partly undercutting the memo's own stated purpose; (b) *memory* — the memo never evicts and holds strong `Arc`s to every keyed `base` **and** `interior` state (and rule) for the whole session, so interior states (which nesting makes into deeper groups' `base`) are pinned alive long after their frame unwinds. Since a session is one transient parse it won't leak across parses, but it's a real per-parse scaling cost. Suggested fix: a `HashMap` keyed on `(Arc::as_ptr(base) as usize, Arc::as_ptr(rule) as usize)` for O(1) lookup — but note the keys must stay held (finding 2), so the retention is somewhat intrinsic and worth a conscious decision.

**2. Ptr-key ABA soundness holds — but only because the memo pins its keys (memoization / design-note) — `mod.rs:45-50, 107-111`.** The doc-comment's claim ("entries hold their key `Arc`s alive, so pointer keys cannot be reused") is correct: because each entry keeps a strong ref to `base` and `rule`, those allocations can't be freed while in the memo, so an incoming live `Arc` whose pointer `ptr_eq`s a stored key is necessarily the same allocation — hence the same logical state; no stale/false hit is possible. The derivation is also a pure function of `(base, rule)` (delta depends only on `rule` via `expecting_group_close`; `finalize_transition` runs over `base` with empty events), so a hit always serves the correct interior. A genuine soundness guarantee, not a latent hazard — but it is exactly the key-retention that drives finding 1; the two are coupled.
